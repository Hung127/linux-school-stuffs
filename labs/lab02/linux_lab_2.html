01
useradd · groupadd · /etc/passwd · /etc/group
Populate a fresh server with users and groups
Warm-up
Scenario

You are a sysadmin onboarding a new project team. The team has two roles: developers (alice, bob) and ops (carol, dave). Set them all up from scratch on a fresh Ubuntu VM.

Tasks
→Create groups dev and ops with groupadd. Verify both appear in /etc/group.
→Create users alice and bob with home directories (-m), bash shell (-s /bin/bash), a GECOS comment (-c "Dev User"), and add them to the dev group (-G dev).
→Create users carol and dave the same way, added to the ops group. Set a password for each user with passwd.
→Run id alice and id carol. Identify the UID, primary GID, and supplementary groups in the output.
→Run grep alice /etc/passwd. Identify all 7 colon-separated fields and state what each one means.
→Create a system user svcapp with no home dir and nologin shell: useradd -r -s /usr/sbin/nologin svcapp. What UID range does it receive? Why is this different?
HintUse useradd -m -s /bin/bash -c "Dev User" -G dev alice then passwd alice. The -G flag at creation time sets supplementary groups directly — no extra usermod needed for new users.

02
usermod · -aG vs -G · lock/unlock · /etc/shadow
The silent group-wipe trap
Warm-up
Scenario

A junior admin tries to add alice to a new group but accidentally runs usermod -G without -a. She loses all her existing groups with no error message. This lab demonstrates the bug and how to fix it.

Tasks
→Add alice to groups dev, docker, and sudo using usermod -aG dev,docker,sudo alice. Confirm all three appear in id alice.
→The trap: run usermod -G qa alice (without -a). Run id alice again. What happened to dev, docker, and sudo?
→Fix it: restore alice to all four groups (dev, docker, sudo, qa) in one command. Verify.
→Run su - alice and then groups inside her shell. Do her active groups reflect the change yet? Run newgrp dev to activate without logging out.
→Lock alice's account with usermod -L alice. Inspect grep alice /etc/shadow — what character appears before her password hash? Unlock with usermod -U alice.
Why it mattersIf alice had sudo access, silently losing the sudo group means she can no longer escalate privileges. usermod -G produces no warning — it is a known footgun.
Deliverables
📷
Screenshotid alice showing 4 groups, then id alice after the -G trap (1 group left).
📷
ScreenshotThe /etc/shadow entry for alice showing the ! lock prefix, then after unlocking.
✍
In reportExplain the difference between -g (lowercase), -G, and -aG. In what real-world scenario would silently losing sudo access cause a serious production outage?
03
chmod · chown · umask · permission evaluation
Read, write, execute — controlling file access
Warm-up
Tasks
→Create secret.txt and directory reports/. Check their default permissions with ls -la. Note the permission string and the current umask.
→Use octal chmod: set secret.txt → 600, reports/ → 750. For each, write out what the three octal digits mean in rwx terms.
→Use symbolic chmod on reports/: add execute for the owner, remove all permissions for others, set group to exactly r-x. Use a single command with a comma-separated list.
→Change the owner of reports/ to alice:dev recursively with chown -R. Verify with ls -la reports/.
→Change the umask to 027 and create a new file and directory. What permissions did they receive? Explain using the formula base − umask.
→Experiment: create a file owned by alice with permissions 640, group dev. Log in as bob (also in dev) and try to read it. Then log in as dave (in ops) and try to read it. Explain why each succeeded or failed.
Permission evaluation orderLinux checks in this exact order — first match wins: (1) root → always granted. (2) UID matches owner → apply owner bits. (3) GID matches group → apply group bits. (4) Otherwise → apply other bits.

04
SUID · SGID · sticky bit · find -perm
Special permission bits: shared directories and elevated execution
Medium
Scenario

The dev team needs a shared folder where all new files automatically belong to the dev group and no one can delete another person's files — even if the directory is group-writable.

Tasks
→Create /opt/teamshared. Set owner to root:dev. Apply mode 3775 (SGID + sticky + rwxrwxr-x). Run ls -ld /opt/teamshared — identify the s and t characters in the output.
→As alice (su - alice), create a file inside /opt/teamshared. Log back out as root and check ls -l /opt/teamshared. What group owns alice's file and why?
→Test the sticky bit: as bob, try to delete alice's file. Confirm it fails. Now remove the sticky bit from the directory (chmod -t) and try again. What changes?
→Restore the sticky bit. Create a small script /tmp/whotest.sh containing echo "Running as: $(whoami)". Set SUID on it (chmod u+s) and make it owned by root. Run it as alice. What identity does it report?
→Find all SUID binaries on the system: find / -perm -4000 2>/dev/null. Identify at least 3 you recognize and explain in your report why each one needs SUID.
Octal for special bitsThe leading digit: 4=SUID, 2=SGID, 1=sticky. Mode 3775 = SGID(2) + sticky(1) = 3, then rwxrwxr-x = 775.

05
setfacl · getfacl · default ACL · mask
Fine-grained access control with ACLs
Medium
Scenario

A project directory needs three distinct access levels: the dev group gets full read/write/execute, the ops group gets read and execute only, and contractor charlie gets read and execute but belongs to neither group. Standard chmod cannot express this — ACLs are the solution.

Tasks
→Create user charlie (no special group). Create /opt/project owned by root:dev, mode 770.
→Apply ACLs: g:dev:rwx, g:ops:r-x, u:charlie:r-x. Run getfacl /opt/project. Also run ls -la and notice the trailing + character.
→Set a default ACL so any new files or subdirectories created inside /opt/project inherit the same permissions: setfacl -d -m g:dev:rwx,g:ops:r-x,u:charlie:r-x /opt/project. As alice, create a file inside and run getfacl on it.
→The mask trap: run chmod g-x /opt/project. Run getfacl /opt/project again. What happened to the effective permissions for dev and charlie? Why?
→Restore the mask by running chmod g+x /opt/project. Then revoke charlie's ACL entirely with setfacl -x u:charlie /opt/project. Confirm with getfacl.
Install ACL tools if neededapt install acl. Modern ext4 filesystems have ACL support enabled by default. Look for the + after the permission string in ls -la to confirm an ACL is set.
Deliverables
📷
ScreenshotFull getfacl /opt/project output showing user, group, mask, and default ACL entries.
📷
Screenshotgetfacl before and after chmod g-x — show the #effective comment change in the mask trap.

06
visudo · sudoers.d · NOPASSWD · least privilege
Grant surgical sudo access to a CI deploy user
Medium
Scenario

An automated CI/CD pipeline runs as user deploy. It needs to execute a deploy script and restart the cron service — nothing else. Granting it full sudo would be a serious security risk.

Tasks
→Create user deploy as a system user with no home and nologin shell: useradd -r -s /usr/sbin/nologin deploy. Confirm you cannot get an interactive shell via su - deploy.
→Create the deploy script: mkdir -p /opt/scripts, then write /opt/scripts/deploy.sh with content echo "Deploying application...". Set permissions 750 and owner root:dev.
→Open visudo -f /etc/sudoers.d/deploy and add a rule allowing the deploy user — without a password — to run only /opt/scripts/deploy.sh and /bin/systemctl restart cron.
→Test (allowed): run sudo -u deploy sudo /opt/scripts/deploy.sh and sudo -u deploy sudo /bin/systemctl restart cron from your admin account. Both should succeed silently.
→Test (denied): run sudo -u deploy sudo /bin/bash and sudo -u deploy sudo rm /etc/passwd. Both should be rejected with a "not allowed" message.
→Check the audit trail: grep "deploy" /var/log/auth.log | tail -20. Find the COMMAND entries for both an allowed run and a denied attempt.
Never edit sudoers directlyAlways use visudo — it validates syntax before saving. A single typo that breaks sudoers requires booting into single-user mode to repair. There is no undo.

07
usermod -L · pkill -u · gpasswd · last · auth.log
Incident response — compromised account containment
Medium
Scenario

Security alerts you: user bob's password was found in a data breach. He is in the sudo and docker groups. You must contain the damage immediately without destroying evidence, then restore his account after the investigation.

Tasks
→Immediate containment — lock the account: run usermod -L bob. Verify the lock by inspecting grep bob /etc/shadow and finding the ! prefix on the password hash.
→Kill active sessions: run pkill -u bob to terminate all of bob's running processes. Confirm with who and ps aux | grep "^bob" that no bob processes remain.
→Revoke elevated access: remove bob from the sudo and docker groups using gpasswd -d bob sudo and gpasswd -d bob docker. Confirm with id bob.
→Audit what bob did: run last bob to see login history. Search grep "bob" /var/log/auth.log for sudo usage. Find files bob owns that were modified recently: find /home/bob -newer /tmp/marker 2>/dev/null (create /tmp/marker with touch -d "1 hour ago" /tmp/marker).
→Recovery: unlock the account (usermod -U bob), expire his password so he must reset it on next login (passwd -e bob), and restore only the docker group (not sudo — per the principle of least privilege).
Lock, don't deleteDeleting the account immediately destroys the UID mapping in file ownership records and log files. Lock first, investigate with evidence intact, delete only after forensics are complete.

08
tmux · sessions · windows · panes · detach/attach
Survive SSH disconnections with tmux
Warm-up
Scenario

You need to run a long data-processing job on a remote server over an unstable SSH connection. If the connection drops mid-run, the job dies. tmux keeps the session alive on the server regardless of what happens to your local terminal.

Tasks
→Create a named session: tmux new -s dataproc. Inside it, start a long job: for i in $(seq 1 300); do echo "Step $i of 300"; sleep 1; done.
→Detach from the session (Ctrl+B then D) while the loop is running. Verify the session is still alive with tmux ls.
→Close your terminal window completely. Reopen a terminal and reattach: tmux attach -t dataproc. Confirm the counter is still incrementing where you left off.
→Split the pane vertically (Ctrl+B %). In the right pane run top. Navigate between panes using Ctrl+B ←→ arrows. Zoom into one pane with Ctrl+B Z and back.
→Create a second window in the same session (Ctrl+B C). Rename it to monitor (Ctrl+B ,). Switch between windows with Ctrl+B 0 / Ctrl+B 1. List all with Ctrl+B W.
→Rename the entire session to lab08 using tmux rename-session lab08. Verify with tmux ls.
tmux vs nohupnohup ./job & keeps one command alive after logout but you lose the interactive shell. tmux gives you a full multi-window, multi-pane workspace you can return to at any time from any terminal.

09
ps · top · kill · nice · renice · signals · jobs
Diagnose and tame a runaway process
Medium
Scenario

A shared lab server is sluggish. CPU is at 99%. Someone left a computation running without any priority setting. Walk through identification, deprioritization, and controlled termination.

Tasks
→Start a CPU hog in the background: python3 -c "while True: pass" &. Note the PID printed by the shell. Confirm it is consuming CPU via top (press P to sort by CPU usage).
→Inspect the process: ps -p <PID> -o pid,comm,user,pcpu,pmem,nice,etime. Record the NI (nice) value and how long it has been running.
→Deprioritize (keep it running): lower its priority with renice -n 19 -p <PID>. Watch the NI column in top change. Does other terminal activity feel more responsive now?
→Signal escalation: send SIGTERM (kill <PID>). Wait 3 seconds and check ps -p <PID>. Since a tight Python loop cannot catch SIGTERM, escalate to SIGKILL (kill -9 <PID>). Confirm it is gone.
→Start a new background job: sleep 999 &. Practice the full job-control cycle: check with jobs, bring to foreground (fg %1), suspend with Ctrl+Z, send to background (bg %1), then kill by job number (kill %1).
→Stretch: launch a new hog with nice -n 10 python3 -c "while True: pass" &. Compare its NI column in top to a default process. Confirm only root can set a negative nice value by trying renice -n -5 -p <PID> as a regular user.
Signal order mattersSIGTERM (15) politely asks the process to clean up and exit. SIGKILL (9) forces instant death with no cleanup. Databases and file-sync services can corrupt data if killed with -9 mid-write — always try SIGTERM first.

Capstone · all concepts
Harden a multi-role development server from scratch
Spicy
Scenario

You are building a shared Linux server for a software team with four roles: developers (write code, deploy), ops (monitor and read logs, no modification), CI runner (automated job account, no login), and auditors (read-only access everywhere, zero write capability). Implement the full security model from user creation to process policy.

Tasks
→Users & Groups: Create groups devs, ops, auditors. Create: alice (devs), carol (ops), eve (auditors), and cirunner as a system user with nologin shell added to devs.
→Project directory: Create /opt/appdata owned by root:devs, mode 2770 (SGID + full group access, no world access). Apply ACL: ops → r-x, auditors → r--. Set default ACL so all new files inherit.
→Log directory: Create /var/log/applog/ owned by root:ops, mode 750. Grant devs write access and auditors read-only via ACL. Set default ACL. Confirm that cirunner (in devs) can write a log entry.
→Sudo policy: Create /opt/scripts/deploy.sh (content: echo "Deploy complete"). In separate sudoers.d files: allow devs group to run /opt/scripts/deploy.sh, allow ops to run /bin/systemctl status cron (read-only check), allow cirunner NOPASSWD for /opt/scripts/deploy.sh. Auditors get no sudo at all.
→Verify access: as alice — write a file to /opt/appdata (should succeed). As carol — try to write to /opt/appdata (should fail). As eve — try to write anywhere (should fail everywhere). Confirm carol can read. Confirm eve can read.
→Security audit: run the three checks from the slide: (a) find any UID=0 accounts besides root with awk -F: '$3==0' /etc/passwd, (b) find world-writable files in /opt, (c) find all SUID binaries you created. Confirm none are unexpected.
→Write-up: document your design in 8–12 sentences. Include a summary table with columns: User | Groups | /opt/appdata | /var/log/applog | sudo rights.
