Slide 2 — Scenario & topology

What you'll build

You'll provision a small server, lock down access to it, deploy a web service, and automate its backups. Each task feeds the next — the rsync backup at the end rides over the same SSH key channel you build in Task 2.

Slide 3 — Task 01

Static IP with nmcli

# 1. inspect the current state
$ ip addr show
$ nmcli con show # find your connection name
$ nmcli device status

# 2. set the static IP (replace CON with the name above)
$ sudo nmcli con mod "CON" \
    ipv4.method manual \
    ipv4.addresses 192.168.56.10/24 \
    ipv4.gateway   192.168.56.1 \
    ipv4.dns      "8.8.8.8 1.1.1.1"

# 3. apply
$ sudo nmcli con up "CON"
Prefer a TUI? sudo nmtui → "Edit a connection" walks the same fields with a menu. Either tool writes the same persistent config.
# 4. verify the address and route
$ ip addr show; ip route show
$ ping -c3 8.8.8.8 # gateway works?
$ ping -c3 google.com # DNS works?
✓ Validation gate

Reboot the VM, log back in, and run ip addr. The static IP must persist. If it reverts, the change didn't save to the connection profile — re-check the connection name in step 1.

If nmcli con show is empty, NetworkManager isn't managing the interface (some Ubuntu Server images use netplan). This lab assumes NetworkManager is in control.
Slide 4 — Task 02

SSH key pair, web-vm → backup-vm

# on web-vm, as deploy: make a modern key pair
$ ssh-keygen -t ed25519 -C "web-vm backup"
  Enter file: ~/.ssh/id_ed25519
  Enter passphrase: ●●●●●●●●

# push the PUBLIC key to backup-vm
$ ssh-copy-id deploy@192.168.56.20

# test — should connect with no password
$ ssh deploy@192.168.56.20 "hostname"
  backup-vm
This is the channel Task 4 uses. Once passwordless SSH works web-vm → backup-vm, rsync can run unattended over it.
Harden backup-vm — /etc/ssh/sshd_config
PasswordAuthentication no
PermitRootLogin no

# test the config, THEN reload
$ sudo sshd -t
$ sudo systemctl reload ssh
Order matters — don't lock yourself out. Copy and test your key before setting PasswordAuthentication no. Keep a second session open while you reload, in case the new config rejects you.
✓ Validation gate

ssh deploy@192.168.56.20 succeeds with the key; password login is refused. Confirm with ssh -o PubkeyAuthentication=no deploy@... → should be denied.

Slide 5 — Task 03

Install nginx, pin the version

# install on web-vm
$ sudo apt update
$ sudo apt install nginx

# confirm it serves
$ nginx -v
$ sudo nginx -t # config OK?
$ curl -I http://localhost # expect 200 OK

# add sample content (Task 4 backs this up)
$ echo "web-vm — v1" | sudo tee /var/www/html/index.html
Why pin? A stray apt upgrade can swap nginx to a new release mid-term and change behaviour. Pinning freezes it until you decide to move.
Pin (hold) the installed version
$ sudo apt-mark hold nginx
$ apt-mark showhold
  nginx

# prove it: an upgrade now skips nginx
$ sudo apt upgrade
  The following held back: nginx
Or install one specific version
$ apt-cache madison nginx # list versions
$ sudo apt install nginx=<version>
# unpin later: sudo apt-mark unhold nginx
✓ Validation gate

curl http://localhost returns your v1 page, and apt-mark showhold lists nginx.

Slide 6 — Task 04 · part 1

Back up web data with rsync

# from web-vm — over the SSH key channel
# 1. ALWAYS dry-run first, especially with --delete
$ rsync -avz --delete -n \
    /var/www/html/ \
    deploy@192.168.56.20:/opt/www-backup/

# 2. real run (drop the -n)
$ rsync -avz --delete \
    /var/www/html/ deploy@192.168.56.20:/opt/www-backup/
  sent 1.2KB  (first run: everything)
Two footguns. The trailing slash on /var/www/html/ copies the contents, not the folder itself. And --delete removes anything on the backup that's gone from the source — which is exactly why the dry run comes first.
# 3. verify on backup-vm
$ ssh deploy@192.168.56.20 "ls -l /opt/www-backup/"

# 4. change a file, run again — only the delta moves
$ echo "web-vm — v2" | sudo tee /var/www/html/index.html
$ rsync -avz --delete /var/www/html/ deploy@...:/opt/www-backup/
  sent 180 bytes  (only the change)
That's the point of rsync: the first run is a full copy; every run after transfers only what changed. Watch the "sent" byte count drop.
✓ Validation gate

The v2 file appears on backup-vm, and a re-run with no changes transfers almost nothing.

Slide 7 — Task 04 · part 2

Automate it — systemd timer

Wrap the command in a script + two units
# /opt/backup-web.sh  (chmod +x, owned by deploy)
#!/usr/bin/env bash
rsync -az --delete /var/www/html/ \
  deploy@192.168.56.20:/opt/www-backup/
# /etc/systemd/system/backup-web.service
[Service]
Type=oneshot
User=deploy # owns the SSH key!
ExecStart=/opt/backup-web.sh
# /etc/systemd/system/backup-web.timer
[Timer]
OnCalendar=hourly
Persistent=true # catch missed runs
[Install]
WantedBy=timers.target
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now backup-web.timer

# when does it next fire?
$ systemctl list-timers backup-web.timer

# run it once now, then read the log
$ sudo systemctl start backup-web.service
$ journalctl -u backup-web.service
The #1 reason this breaks: the service runs as a user that doesn't own the SSH key. The key lives in deploy's ~/.ssh, so the unit must set User=deploy — otherwise it runs as root and can't authenticate.
Prefer cron? Same job, one line: 0 * * * * /opt/backup-web.sh in crontab -e. The timer wins on logging — journalctl shows every run.
Slide 8 — Wrap-up

Prove it works & submit

Final checklist — all four tasks
[✓]01  web-vm holds 192.168.56.10 after a reboot
[✓]02  Passwordless SSH web-vm → backup-vm; password login refused
[✓]03  curl localhost serves your page; apt-mark showhold lists nginx
[✓]04  Editing the page and waiting an hour updates /opt/www-backup; journalctl shows the run
3 mistakes that cost the most time:
1. PasswordAuthentication no set before the key was copied → locked out
2. rsync --delete with no dry run → wiped the backup
3. Timer service left as root → silent auth failures every hour
