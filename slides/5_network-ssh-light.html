Slide 3 — Theory

Network Interfaces — ip & nmcli

# inspect current state
$ ip addr show # all interfaces
$ ip addr show eth0 # specific iface
$ ip route show # routing table
$ ip link show # layer-2 status
# temporary IP assignment (lost on reboot)
$ ip addr add 192.168.1.100/24 dev eth0
$ ip route add default via 192.168.1.1
# nmcli — persistent config
$ nmcli con show # list connections
$ nmcli device status
# set static IP
$ nmcli con mod "Wired connection 1" \
ipv4.method manual \
ipv4.addresses 192.168.1.100/24 \
ipv4.gateway 192.168.1.1 \
ipv4.dns "8.8.8.8 8.8.4.4"
$ nmcli con up "Wired connection 1"
DHCP vs Static IP
DHCPStatic
AssignmentAutomaticManual
Changes?May change on leaseNever changes
Use forWorkstations, dev VMsServers, services
DNS entryDynamic (tricky)Stable, mappable
Servers always get static IPs. If a server's IP changes, every service pointing to it breaks — DNS records, firewall rules, SSH known_hosts.
ip commands are from the iproute2 suite and replace the deprecated ifconfig. Use ip on all modern systems.

Network Diagnostics

# connectivity tests
$ ping -c 4 8.8.8.8 # ICMP test
$ traceroute 8.8.8.8 # hop-by-hop path
$ mtr 8.8.8.8 # live traceroute
# open ports and sockets
$ ss -tlnp # listening TCP
$ ss -ulnp # listening UDP
$ ss -tnp state established # active conns
# older equivalent (deprecated)
$ netstat -tlnp # use ss instead
ss flags cheatsheet
FlagMeaning
-tTCP sockets
-uUDP sockets
-lListening only
-nNo name resolution (faster)
-pShow process name/PID
# HTTP testing with curl
$ curl -I https://example.com # headers only
$ curl -v https://example.com # verbose (TLS info)
$ curl -o /dev/null -sw "%{http_code}\n" URL
# check if port is reachable
$ nc -zv 192.168.1.10 22 # TCP port check
$ nc -zv 192.168.1.10 80

$ wget -q -O- https://example.com/file
$ wget --continue https://large-file.iso
Diagnosis order: ping (reachable?) → nc (port open?) → curl (service responds?) → ss (what's listening locally?). Each step narrows the problem.

UFW — Host Firewall Basics

# check status (numbered rules)
$ ufw status verbose
$ ufw status numbered
# the safe default: deny in, allow out
$ ufw default deny incoming
$ ufw default allow outgoing
# ALLOW SSH *before* enabling — or lock yourself out
$ ufw allow 22/tcp
$ ufw allow 80,443/tcp # web
# limit = allow but throttle brute-force (6/30s)
$ ufw limit 22/tcp
# turn it on
$ ufw enable
# delete a rule by number
$ ufw delete 3
The #1 self-inflicted outage. Enabling a default-deny firewall before allowing port 22 drops your own SSH session instantly — and you can't reconnect. Always ufw allow 22 first.
Scope a rule to a source — much safer
# only the office network may reach SSH
$ ufw allow from 203.0.113.0/24 to any port 22
# only the app server may reach the DB
$ ufw allow from 10.0.0.30 to any port 5432
# deny a known-bad IP outright
$ ufw deny from 198.51.100.7
UFW vs the firewall underneath

UFW is a friendly front-end for iptables/nftables. It is perfect for a single host. For routing between networks, NAT, or cloud fleets you'll meet the raw tools or a cloud "security group" — the same deny-by-default idea, different control panel.

Defense in depth. A cloud security group and the host's UFW are two locks on the same door. If one is misconfigured, the other still holds.
Slide 6 — Theory

SSH Key Pairs — How Authentication Works

Key pair — public vs private
🔓
Public Key
~/.ssh/id_ed25519.pub
Lives on the server
in authorized_keys
Safe to share
🔑
Private Key
~/.ssh/id_ed25519
Stays on your laptop
NEVER share this
Protect with passphrase
Analogy: The public key is a padlock you give to the server. Your private key is the only key that opens it. Even if someone steals the padlock, they can't open it.
# generate a new key pair (ed25519 is modern)
$ ssh-keygen -t ed25519 -C "alice@laptop"
Generating public/private ed25519 key pair
Enter file: ~/.ssh/id_ed25519
Enter passphrase: ●●●●●●●●
# copy public key to server
$ ssh-copy-id -i ~/.ssh/id_ed25519.pub alice@192.168.1.10
# manual alternative
$ cat ~/.ssh/id_ed25519.pub | ssh alice@server \
"mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"
# now login — no password needed
$ ssh alice@192.168.1.10
Always set a passphrase on your private key. Use ssh-agent so you only type it once per session, not per connection.

Slide 7 — Theory

sshd_config — Server Hardening

/etc/ssh/sshd_config — key settings
# non-default port (less automated scanning)
Port 2222
# MUST disable root login
PermitRootLogin no
# keys only — no password brute force possible
PasswordAuthentication no
PubkeyAuthentication yes
# whitelist who can log in
AllowUsers alice bob deploy
# disconnect idle sessions (5min timeout)
ClientAliveInterval 300
ClientAliveCountMax 2
# apply changes
$ sshd -t # test config first!
$ systemctl reload ssh
Impact of each change
SettingSecurity effect
Port 2222Drops ~95% of automated scan traffic
PermitRootLogin noRoot can't be targeted directly
PasswordAuth noBrute force attacks become impossible
AllowUsersEven compromised accounts can't SSH in
Test config before reloading. Run sshd -t to catch syntax errors. Keep a second terminal session open — it stays alive even if sshd restarts.
After disabling password auth, ssh-copy-id won't work. Always copy your public key before setting PasswordAuthentication no.
Slide — Theory

fail2ban — Auto-Ban Brute Force

The problem it solves

A public SSH port gets thousands of login attempts a day from bots. Keys defeat the attack, but the noise floods your logs and wastes CPU. fail2ban watches the log and bans an IP in the firewall after N failures.

# install
$ apt install fail2ban
# /etc/fail2ban/jail.local (never edit jail.conf)
[sshd]
enabled = true
port = 2222 # match your sshd port
maxretry = 4 # fails before ban
findtime = 10m # ...within this window
bantime = 1h # how long banned
bantime.increment = true # repeat = longer
# apply and watch
$ systemctl restart fail2ban
$ fail2ban-client status sshd
Currently failed: 3
Currently banned: 12
Banned IP list: 61.177.. 218.92.. ...
# unban an IP (e.g. you fat-fingered it)
$ fail2ban-client set sshd unbanip 1.2.3.4
# whitelist your office so you're never banned
ignoreip = 127.0.0.1/8 203.0.113.0/24
Layered with keys. Keys stop the break-in; fail2ban stops the noise and the CPU drain. UFW limit is a lighter alternative; fail2ban is smarter (reads the log, escalates bans).
Whitelist yourself first. Add your own network to ignoreip before you trust the bans — otherwise one bad night of typos locks you out of your own server.

~/.ssh/config — Connection Aliases

~/.ssh/config
# use: ssh web
Host web
HostName 192.168.1.10
User alice
Port 2222
IdentityFile ~/.ssh/id_ed25519
# use: ssh db
Host db
HostName 192.168.1.20
User alice
Port 2222
# defaults for all hosts
Host *
ServerAliveInterval 60
IdentityFile ~/.ssh/id_ed25519
Before vs after ~/.ssh/config
# BEFORE — type all this every time
$ ssh -i ~/.ssh/id_ed25519 \
-p 2222 alice@192.168.1.10
# AFTER — clean alias
$ ssh web
# also works for scp and rsync
$ scp web:/var/log/nginx/access.log .
$ rsync -avz web:/opt/app/ ./backup/
Permissions matter. SSH is strict about file permissions. Run: chmod 600 ~/.ssh/config and chmod 700 ~/.ssh/ or SSH will refuse to use them.
The config also works for tools that use SSH under the hood: git, rsync, ansible, kubectl port-forward — all respect ~/.ssh/config.

ProxyJump — Bastion Host Pattern

Enterprise network topology
💻 Laptop
Your Machine
encrypted tunnel
🏰 Bastion
Public IP
internal network
🖥 web-01
10.0.0.10
🗄 db-01
10.0.0.20

Only the bastion has a public IP. Internal servers are unreachable from the internet directly — you must go through bastion.

# one-liner ProxyJump
$ ssh -J alice@bastion.company.com alice@10.0.0.10
# in ~/.ssh/config — cleaner
Host bastion
HostName 203.0.113.10 # public IP
User alice
Host web-01
HostName 10.0.0.10 # private IP
User alice
ProxyJump bastion
Host db-01
HostName 10.0.0.20
User alice
ProxyJump bastion
# now just:
$ ssh web-01 # transparently jumps via bastion
$ ssh db-01
This is the real enterprise model. Your private key never leaves your laptop — even bastion can't read it. SSH agent forwarding is an alternative but less secure.
Slide — Theory

SSH Tunneling — Port Forwarding

Local forward (-L) — bring a remote port to you

A database listens only on the server's localhost. Open it on your machine's port 5433 — safely, through SSH.

$ ssh -L 5433:localhost:5432 alice@server
# now on your laptop:
$ psql -h localhost -p 5433
→ tunnels to server's 5432, encrypted
Remote forward (-R) — expose your port to the server

Let a remote machine reach a service running on your laptop (e.g. a webhook in dev).

$ ssh -R 8080:localhost:3000 alice@server
→ server:8080 reaches your laptop:3000
Dynamic forward (-D) — a quick SOCKS proxy

Route your browser through the server — useful to test geo-specific behaviour or reach an internal site.

$ ssh -D 1080 alice@server
# point browser SOCKS5 → localhost:1080
Mnemonic. -L = "pull a port Local". -R = "push a port Remote". -D = "Dynamic proxy for everything".
Keep it alive & in the background. Add -fN to background a pure tunnel with no shell. On the server, GatewayPorts and AllowTcpForwarding in sshd_config decide what forwarding is permitted — leave them off unless needed.
Why it matters. Tunnels let you reach internal services without opening new firewall ports — the encrypted SSH channel is the access path.
Slide 10 — Theory

scp & rsync — File Transfer Over SSH

scp — simple file copy
# local → remote
$ scp report.pdf alice@web:/tmp/
# remote → local
$ scp alice@web:/var/log/nginx/access.log .
# copy directory recursively
$ scp -r ./project/ alice@web:/opt/
# uses ~/.ssh/config aliases
$ scp web:/etc/nginx/nginx.conf .
scp for one-off copies, rsync for sync. scp always transfers everything. rsync is smart — it only sends what changed. Use rsync for anything recurring.
rsync — incremental sync
# sync local dir to remote
$ rsync -avz ./web/ alice@backup:/opt/web/
# sync with delete (mirror)
$ rsync -avz --delete ./web/ alice@backup:/opt/web/
# dry run first — see what would change
$ rsync -avzn ./web/ alice@backup:/opt/web/
# exclude patterns
$ rsync -avz --exclude '*.log' --exclude '.git/' \
./web/ alice@backup:/opt/web/
# bandwidth limit (KB/s)
$ rsync -avz --bwlimit=1000 ./large/ remote:/dest/
rsync flags
FlagMeaning
-aArchive: preserve perms, times, symlinks
-vVerbose — show transferred files
-zCompress data during transfer
-nDry run — no actual changes
--deleteRemove files not in source

When SSH Won't Connect — Common Errors

Error you seeUsual cause & fix
Permission denied (publickey)Key not in authorized_keys, or wrong key offered. Debug: ssh -v. Fix: ssh-copy-id or -i.
Connection refusedsshd not running, or wrong port. Check systemctl status ssh and the Port.
Connection timed outFirewall/security group blocks the port, or host unreachable. Check UFW & cloud rules.
Too many auth failuresssh-agent offered too many keys. Use -o IdentitiesOnly=yes -i key.
The scary one — host key changed
@@@ WARNING: REMOTE HOST IDENTIFICATION
HAS CHANGED! @@@
Someone could be eavesdropping ...
# legit cause: server was rebuilt / reinstalled
$ ssh-keygen -R server-hostname
# then reconnect and accept the new key
Don't blindly clear it. This warning is also exactly what a man-in-the-middle attack looks like. Only remove the old key if you know the server was legitimately rebuilt. If not, stop and investigate.
The permission trap. SSH refuses keys that are too open. chmod 600 ~/.ssh/id_ed25519 and 700 ~/.ssh. A world-readable private key is silently ignored.
Slide 11 — Real-world examples

Examples: SSH Keys & rsync in Practice

Scenario 1 — passwordless CI/CD deployment

A GitHub Actions pipeline needs to deploy to your server. You add the deploy key once — no password stored in CI.

# on server: add CI's public key
$ echo "ssh-ed25519 AAAA... ci@github" \
>> /home/deploy/.ssh/authorized_keys
# GitHub Actions pipeline can now:
$ ssh deploy@yourserver.com "./deploy.sh"
$ rsync -avz ./dist/ deploy@server:/opt/app/
Scenario 2 — ProxyJump in real life

Your company has a bastion at jump.company.com. All production servers are private.

# one command, two hops
$ ssh prod-web-01
→ connecting to jump.company.com...
→ connecting to 10.10.1.50...
alice@prod-web-01:~$
Scenario 3 — hourly rsync backup via cron

Sync the web directory to a backup server every hour. Only changed files are transferred — fast even over slow links.

# crontab -e
0 * * * * rsync -avz --delete \
/var/www/html/ \
backup:/opt/www-backup/ \
>> /var/log/rsync.log 2>&1
# first run: transfers everything
sent 150MB in 45s
# subsequent runs: only changes
sent 45KB in 0.3s
--delete with caution. Always do a dry run with -n first when using --delete. It will remove files from the destination that don't exist in the source.
Slide — Case Study

Case Study: Securing Your First VPS

You just rented a $5/month VPS for a class project. It arrives with root + a password emailed in plaintext — the least secure possible state. Here is the 10-minute checklist to do first, every time.

# 1. from YOUR laptop — make a key if needed
$ ssh-keygen -t ed25519 -C "myname@laptop"
# 2. copy it up (last time you use the password)
$ ssh-copy-id root@your.vps.ip
# 3. make a normal user with sudo (not root!)
$ adduser mmt
$ usermod -aG sudo mmt
$ ssh-copy-id mmt@your.vps.ip
# 4. test the new user BEFORE locking root
$ ssh mmt@your.vps.ip "sudo whoami"
root ✓
# 5. /etc/ssh/sshd_config — lock it down
PermitRootLogin no
PasswordAuthentication no
AllowUsers mmt
# 6. ALWAYS test config before reload
$ sshd -t
$ systemctl reload ssh
# 7. firewall: SSH + web only
$ ufw allow 22/tcp
$ ufw allow 80,443/tcp
$ ufw enable
Keep the first session open. After reloading sshd, open a second terminal and confirm you can still log in — before closing the first. If you broke something, the open session is your lifeline back in.
Every concept, one box. Keys (Slide 6), hardening (7), user+sudo (Module 2), firewall (UFW). A real server touches the whole module.

Case Study: Server Under SSH Brute-Force

3am: monitoring flags one VPS at 100% CPU and auth.log is exploding. Walk through detection → containment → hardening — without taking the box offline.

1 — Detect
# who is hammering us?
$ grep "Failed password" \
/var/log/auth.log | wc -l
8471
# top offender IPs
$ grep "Failed password" auth.log \
| grep -oE "[0-9.]+" \
| sort | uniq -c | sort -rn
6120 61.177.x.x
2 — Contain
# block the worst IP now
$ ufw deny from 61.177.x.x
# did anyone actually get in?
$ grep "Accepted" auth.log
$ last | head
$ who # active sessions now
# if a breach: lock + kill (Module 2)
$ pkill -u baduser
3 — Harden
# keys only, no passwords
PasswordAuthentication no
PermitRootLogin no
# install the auto-banner
$ apt install fail2ban
$ ufw limit 22/tcp
# verify, then reload
$ sshd -t && systemctl reload ssh
The lesson. The bots never stop — your job is to make the attack pointless. Password auth off = brute force can't win; fail2ban + ufw limit = the noise and CPU drain disappear. After hardening, 8,000 attempts/day become a non-event.
Slide 12 — Hands-on labs

Lab Exercises

01
Configure static IP with nmcli
1. Check current IP: ip addr show
2. Identify your connection name: nmcli con show
3. Set static IP, gateway, and DNS
4. Bring connection up: nmcli con up "..."
5. Verify: ip addr and ping 8.8.8.8
Reboot and confirm the IP persists
02
SSH key pair — passwordless login between 2 VMs
1. On VM-A: ssh-keygen -t ed25519
2. Copy to VM-B: ssh-copy-id user@VM-B-IP
3. Test: ssh user@VM-B-IP — no password
4. On VM-B: harden sshd_config
5. Test again — key auth should still work
Verify PasswordAuthentication no blocks password login
03
Configure ~/.ssh/config with aliases
1. Create ~/.ssh/config with at least 2 Host entries
2. Set correct permissions: chmod 600 ~/.ssh/config
3. Connect using alias: ssh vm-a, ssh vm-b
4. Test scp with alias: scp vm-b:/etc/hostname .
Bonus: add a Host * block with ServerAliveInterval 60
04
rsync web dir to backup VM + cron
1. Create sample files in /var/www/html/ on VM-A
2. rsync to VM-B: test with -n first
3. Run without -n, verify files appear on VM-B
4. Add to crontab: every minute for testing
5. Modify a file on VM-A, wait — check VM-B
Change cron to hourly (0 * * * *) when done
05
Harden SSH: firewall + fail2ban
1. ufw allow 22/tcp — then ufw enable (order matters!)
2. Set PasswordAuthentication no, test with sshd -t, reload
3. Install fail2ban; set maxretry=3 in jail.local
4. From another host, fail login 3× — confirm the ban
Check: fail2ban-client status sshd. Unban yourself after.
06
SSH tunnel to a private service
1. On VM-B run a service on localhost only (e.g. python3 -m http.server 8000)
2. From VM-A: ssh -L 9000:localhost:8000 vm-b
3. Open localhost:9000 on VM-A — reaches VM-B's service
4. Add -fN to background the tunnel
Bonus: explain why VM-B's port was never firewall-exposed
Slide 13 — Summary

Key Takeaways

Servers need static IPs. Use nmcli for persistent config. A server that changes its IP breaks DNS, firewalls, and SSH known_hosts all at once.

SSH keys over passwords, always. Keys are cryptographically stronger and eliminate the entire class of brute-force attacks. Set a passphrase and use ssh-agent.

~/.ssh/config saves hours. Aliases, ProxyJump chains, and per-host keys in one file. Every tool that uses SSH respects it.

rsync for recurring transfers. Always dry run with -n first, especially with --delete. Combine with cron for automated backups.

Commands to memorize
ip addrip routenmcli con mod digss -tlnpnc -zv ssh-keygen -t ed25519ssh-copy-id sshd -tsystemctl reload ssh ufw limit 22fail2ban-client ssh -L / -R / -Dssh -J bastion scp -rrsync -avzrsync --delete
3 mistakes that lock you out:
1. Setting PasswordAuthentication no before copying your key
2. Editing sshd_config without testing with sshd -t
3. Running rsync --delete without a dry run first
Defense in depth wins. Keys + sshd hardening + UFW + fail2ban are four independent locks. An attacker must defeat all of them. Next session: system auditing & log aggregation (auditd, Lynis).
