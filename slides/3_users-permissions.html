Slide 3 — Theory

User & Group Management

# create user with home dir + bash shell
$ useradd -m -s /bin/bash alice
$ passwd alice
# create user, set expiry, comment
$ useradd -m -s /bin/bash -c "Dev User" -e 2025-12-31 bob
# create group, then add alice
$ groupadd dev
$ usermod -aG dev alice
# change primary group (-g lowercase)
$ usermod -g developers alice
# verify memberships
$ id alice
uid=1001(alice) gid=1001(alice) groups=1001(alice),1002(dev)
# lock / unlock an account
$ usermod -L alice # lock
$ usermod -U alice # unlock
# delete user + home dir
$ userdel -r alice
-aG is critical. Without -a, usermod -G replaces all existing groups — potentially revoking sudo access silently.
Key System Files

/etc/shadowhashed passwords, aging policyroot only

/etc/passwd format — 7 fields
alice:x:1001:1001:Dev User:/home/alice:/bin/bash
#name :x :uid :gid :comment :home :shell
System users (UIDs 0–999) run services like nginx, postgres, www-data — they typically have /usr/sbin/nologin as their shell to prevent interactive login.

umask — default permission mask

New files inherit: base − umask. Files base = 666, Dirs base = 777.

umaskFiles getDirs getUse case
022644755default (most systems)
027640750stricter, no world read

Permission Evaluation Order

Linux checks in this exact order — first match wins:

1 Are you root? → access granted always
2 UID matches owner? → apply owner bits
3 GID matches group? → apply group bits
4 Otherwise → apply other bits
Avoid chmod 777. World-writable files let any local user overwrite them — a critical security risk in production.
Slide 5 — Theory

Special Permission Bits

SUID

Set User ID

Run the file with the file owner's privileges, not the caller's.

# set SUID (octal: 4xxx)
$ chmod u+s /usr/bin/passwd
$ chmod 4755 myapp
-rwsr-xr-x /usr/bin/passwd
# 's' = SUID set + exec
# 'S' = SUID set, NO exec
/usr/bin/passwd must run as root to write /etc/shadow, but any user should be able to change their own password.
Security: SUID on shell binaries is a privilege escalation vector. Audit with: find / -perm -4000 2>/dev/null
SGID

Set Group ID

On files: runs with owner's group. On directories: new files inherit the dir's group.

# SGID on directory (octal: 2xxx)
$ chmod g+s /opt/project
$ chmod 2775 /opt/project
drwxrwsr-x /opt/project
# alice (in dev) creates a file:
$ touch /opt/project/notes.txt
-rw-r--r-- alice dev notes.txt
Without SGID, new files would belong to alice's primary group — breaking team access to shared directories.
Sticky

Sticky Bit

On directories: users can only delete their own files, even if they have write access to the dir.

# set sticky bit (octal: 1xxx)
$ chmod +t /shared
$ chmod 1777 /shared
drwxrwxrwt /tmp
# bob can NOT delete alice's file:
bob$ rm /tmp/alice.txt
rm: cannot remove: Operation not permitted
/tmp has sticky bit by default. Everyone writes temp files, but only each user can delete their own.
Slide 6 — Theory

Extended ACLs — Fine-Grained Access

Traditional chmod only supports owner / group / others. ACLs let you define permissions for any specific user or group.
# grant specific user access
$ setfacl -m u:alice:rwx /opt/project
# grant group access
$ setfacl -m g:dev:rwx /opt/project
$ setfacl -m g:ops:r-x /opt/project
# default ACL (new files inherit)
$ setfacl -d -m g:dev:rwx /opt/project
# recursive apply
$ setfacl -R -m u:alice:rx /var/log/app
# remove a specific entry
$ setfacl -x u:alice /opt/project
# remove ALL ACLs
$ setfacl -b /opt/project
# view ACLs
$ getfacl /opt/project
getfacl output explained
# file: opt/project
# owner: alice
# group: dev
user::rwx # owner permissions
user:bob:r-x # named user ACL
group::rwx # owning group
group:ops:r-x # named group ACL
mask::rwx # effective max for ACL entries
other::--- # everyone else: no access
The mask trap. Running chmod g-x /opt/project after setting ACLs silently reduces the mask, capping all named entries' effective permissions — even if their ACL says rwx.
The + indicator. ls -l shows a trailing + on files with ACLs: drwxrwxr-x+
chmod vs setfacl. Use chmod for simple owner/group/other rules. Reach for setfacl when you need different access for multiple distinct users or groups on the same path.
Slide 7 — Theory

sudo & Least Privilege

The Principle

Every user should have access to exactly what they need — nothing more. sudo is the enforcement mechanism with a full audit trail.

no root logingranular controlfull audit trail
# NEVER edit sudoers directly!
$ visudo # validates syntax on save
$ visudo -f /etc/sudoers.d/deploy
# Syntax: user host=(runas:group) cmds
# Full sudo access
alice ALL=(ALL:ALL) ALL
# Group sudo (% prefix)
%admin ALL=(ALL:ALL) ALL
# No-password for specific command
deploy ALL=(root) NOPASSWD: /bin/systemctl restart nginx
# Multiple commands
bob ALL=(root) NOPASSWD: /bin/systemctl restart nginx, /bin/systemctl reload nginx
# Run as specific user
carol ALL=(www-data) /usr/bin/php /var/www/cron.php
Sudoers rule anatomy
deploy   ALL = ( root )   NOPASSWD:   /bin/systemctl restart nginx
who
from host
run as
no passwd
which command
Real-world — CI/CD deploy user
# deploy script runs automatically
$ sudo systemctl restart nginx
✓ Restarted (no password prompt)
# any other command is denied
$ sudo rm -rf /
Sorry, user deploy is not allowed to
execute '/bin/rm -rf /'
Always use visudo. A single typo in sudoers can lock everyone out of sudo. visudo validates before saving and locks the file to prevent concurrent edits.
Prefer /etc/sudoers.d/. Add separate files per user/service. Easier to audit, easier to remove — and you never touch the base sudoers file.
Slide 8 — Theory

tmux — Persistent Terminal Sessions

The Problem

SSH connection drops → all running processes in that session die. Compilation, migrations, log tailing — all lost.

# session management
$ tmux new -s mysession # create named session
$ tmux ls # list sessions
$ tmux attach -t mysession # reattach
$ tmux kill-session -t mysession
# rename current session
$ tmux rename-session deploy
# switch between sessions
$ tmux switch -t other-session
tmux workflow — survive SSH drops
1tmux new -s migrationcreate session
2./db-migrate.shrun long job
3Ctrl+B Ddetach safely
4internet drops...session stays alive
5tmux attach -t migrationstill running!

Process Management

Viewing & inspecting processes
# snapshot — all processes
$ ps aux
# process tree
$ ps auxf
# find process by name
$ ps aux | grep nginx
$ pgrep nginx # returns PIDs only
# live monitoring
$ top # classic (q to quit)
$ htop # visual, mouse-friendly
# show process file handles
$ lsof -p 1234
Signals — communicating with processes
SignalNumberMeaning
SIGTERM15Graceful shutdown (default)
SIGKILL9Force kill — cannot be caught
SIGHUP1Reload config (no restart)
SIGSTOP19Pause process (Ctrl+Z)
SIGCONT18Resume paused process
# kill by PID
$ kill 1234 # SIGTERM (graceful)
$ kill -9 1234 # SIGKILL (force)
$ kill -HUP 1234 # reload config
# kill by name
$ pkill nginx # SIGTERM to all nginx
$ pkill -9 nginx # force kill
$ killall nginx # same effect
Priority — nice & renice

Nice values: -20 (highest priority) to +19 (lowest). Default = 0. Only root can set negative values.

# start with low priority
$ nice -n 10 ./heavy-job.sh
# change running process priority
$ renice -n 5 -p 1234
# background / foreground jobs
$ ./build.sh & # start in background
$ jobs # list bg jobs
$ fg %1 # bring job 1 to fg
# Ctrl+Z suspends, then 'bg' resumes
SIGKILL last resort. It skips cleanup — open files may be left in inconsistent state. Always try SIGTERM first and give the process a few seconds.

The -G trap — demonstrated:
alice currently in: sudo, docker, dev
usermod -G newgroup alice → now ONLY in: newgroup
Alice just lost sudo and docker access silently.
Re-login required. After usermod -aG, the user must log out and back in (or run newgrp groupname) for the new group to appear in their active session.
Primary (-g) vs Supplementary (-aG)
# -g changes PRIMARY group
# Affects ownership of NEW files
$ usermod -g developers alice
$ touch /tmp/test
-rw-r--r-- alice developers test
# ^^^^^^^^^^^ primary group
# -aG adds SUPPLEMENTARY group
# Affects what resources you can access
$ usermod -aG docker alice
# now alice can run docker commands
# (docker socket owned by docker group)
# Move home dir safely
$ usermod -d /data/alice -m alice
# -m also moves the existing home contents
# Rename user (login name only)
$ usermod -l alice_smith alice
# home dir and files still say 'alice'
# use -d -m to fix home dir too
# Verify group membership
$ groups alice
$ id alice
# changes take effect on NEXT login

Common permission patterns
ModeUse case
600Private key files (.ssh/id_rsa)

700Private scripts, home dirs

770Shared team directory
640Config with group read

Symbolic mode — operators & targets

TARGETS

u = user (owner)
g = group
o = others
a = all (u+g+o)

OPERATORS

+ = add permission
- = remove permission
= = set exactly
$ chmod u+x run.sh # owner: add exec
$ chmod g=rx script # group: exactly rx
$ chmod o-rwx private # others: remove all
$ chmod a-x data.csv # all: remove exec
$ chmod ug+rw,o=r doc # combo
Execute on directories. The x bit on a directory means "enter" (traverse). Without it, even r lets you list file names but not access them. This is how you create a directory that's listable but not traversable.
Slide 12 — Real-world Examples

Putting It All Together

Scenario 1 — /tmp sticky bit

Every user writes temp files to /tmp. Without sticky bit, anyone could delete anyone else's files.

$ ls -ld /tmp
drwxrwxrwt — 't' = sticky bit
# bob cannot delete alice's file
bob$ rm /tmp/alice-report.txt
rm: cannot remove: Operation not permitted
Scenario 2 — Shared project dir with ACL
# setup once by admin
$ mkdir /opt/project
$ chown root:dev /opt/project
$ chmod 2770 /opt/project # SGID + rwx for group
$ setfacl -m g:dev:rwx /opt/project
$ setfacl -m g:ops:r-x /opt/project
$ setfacl -d -m g:dev:rwx /opt/project
Scenario 3 — Limited sudo for deploy user
# /etc/sudoers.d/deploy (via visudo -f)
deploy ALL=(root) NOPASSWD:
/bin/systemctl restart nginx,
/bin/systemctl reload nginx
# deploy script can now do:
$ sudo systemctl restart nginx ✓
$ sudo systemctl stop nginx ✗ denied
Scenario 4 — Long-running job via tmux
$ tmux new -s migration
$ ./db-migrate.sh # takes 2 hours
# internet drops — no problem
# ssh back in and:
$ tmux attach -t migration
Migration still running: 73% complete
Slide 13 — Case Study

Case Study: Hardening a Web Server

A new Ubuntu server running nginx needs to be configured so developers can deploy code, operations can monitor logs, and the web process runs with minimal privilege.

Step 1 — Users & Groups
# nginx runs as www-data (system user)
# already exists: uid=33
# create groups
$ groupadd webdev
$ groupadd webops
# create deploy user (no home needed)
$ useradd -r -s /usr/sbin/nologin deploy
$ usermod -aG webdev deploy
# add human users
$ usermod -aG webdev alice
$ usermod -aG webops carol
Step 2 — Directory Permissions
# web root — www-data reads, dev writes
$ mkdir /var/www/myapp
$ chown www-data:webdev /var/www/myapp
$ chmod 2775 /var/www/myapp
# SGID: new files inherit webdev group
# config — only root writes, www-data reads
$ chmod 640 /etc/nginx/nginx.conf
$ chown root:www-data /etc/nginx/nginx.conf
# logs — ops reads, nginx writes
$ chown www-data:webops /var/log/nginx
$ chmod 750 /var/log/nginx
Step 3 — ACL & sudo
# ops: read-only on web root
$ setfacl -Rm g:webops:r-x /var/www/myapp
# deploy sudo — only restart/reload
$ visudo -f /etc/sudoers.d/deploy
deploy ALL=(root) NOPASSWD:
/bin/systemctl restart nginx,
/bin/systemctl reload nginx
# verify final state
$ getfacl /var/www/myapp
$ ls -la /var/www/myapp
Result: www-data serves files. webdev deploys code. webops monitors logs. deploy restarts nginx. No user has more than they need.
Slide 14 — Case Study

Case Study: Responding to a Compromised Account

You discover that user bob's credentials were leaked. He has sudo access and is in the docker group. Walk through containment and recovery.

Phase 1 — Immediate Containment
# 1. Lock account immediately
$ usermod -L bob
# prepends '!' to hash in /etc/shadow
# 2. Kill active sessions
$ pkill -u bob # kill all bob's procs
$ who # check active logins
# 3. Revoke sudo immediately
$ visudo -f /etc/sudoers.d/bob
# comment out or delete bob's entry
# 4. Remove from sensitive groups
$ gpasswd -d bob docker
$ gpasswd -d bob sudo
Why lock, not delete? Deleting immediately destroys audit evidence. Lock first, investigate, delete only after forensics are complete.
Phase 2 — Audit & Recovery
# Check what bob ran recently
$ last bob # login history
$ grep bob /var/log/auth.log
$ grep bob /var/log/sudo.log
# Check for files created/modified
$ find / -user bob -newer /tmp/marker
# Check crontabs for persistence
$ crontab -u bob -l
# After investigation — reset & restore
$ usermod -U bob # unlock
$ passwd -e bob # force password change
$ usermod -aG docker bob # restore groups
Lesson: Least privilege limits blast radius. If bob only had access to his project dir and one sudo command, a compromise would be far less damaging than if he had full sudo.
Slide 15 — Case Study

Case Study: Runaway Process Investigation

A server is slow and unresponsive. CPU at 99%. Walk through diagnosis and resolution without rebooting.

Phase 1 — Identify
# Find the CPU hog
$ top # press P to sort by CPU
$ ps aux --sort=-%cpu | head -10
# Identify what the process is
$ ps -p 8432 -o comm,args,user
COMMAND ARGS USER
python3 /home/alice/ml-train.py alice
# How long has it been running?
$ ps -p 8432 -o etime,pcpu,pmem
ELAPSED %CPU %MEM
06:42:11 98.7 31.2
# Check open files / network
$ lsof -p 8432
$ strace -p 8432 # what syscalls is it making?
Phase 2 — Resolve
# Option A: deprioritize (keep running)
# Lower CPU priority — system stays responsive
$ renice -n 19 -p 8432
8432 (process ID) old priority 0, new priority 19
# Option B: graceful stop
$ kill 8432 # SIGTERM — wait a few sec
$ ps -p 8432 # check if it exited
# Option C: force kill (last resort)
$ kill -9 8432
# Prevent recurrence — use nice at launch
$ nice -n 15 python3 ml-train.py &
Best practice. Long CPU-intensive jobs should always be launched with nice -n 10 or higher. This reserves priority for interactive and service processes.
Root vs user renice. Only root can set negative nice values (increase priority). Regular users can only lower their own process priorities.
Slide 16 — Best Practices

Security Best Practices

Users & Groups
✓ Never use root for daily work
✓ One user per service (www-data, postgres)
✓ Use -r flag for system users
✓ Set nologin shell for service accounts
✓ Lock unused accounts (usermod -L)
✓ Manage via groups, not individuals
✗ Never share accounts between people
✗ Never add service users to sudoers
Audit regularly:
cat /etc/passwd | awk -F: '$3 == 0'
Should only show root (UID 0).
Permissions
✓ Use 600 for private keys
✓ Use 644/755 as sensible defaults
✓ SGID on all shared directories
✓ Sticky bit on world-writable dirs
✓ Verify with ls -la + getfacl
✗ Never chmod 777 in production
✗ Don't SUID scripts (only binaries)
✗ Audit SUID/SGID files periodically
# find all SUID binaries
$ find / -perm -4000 2>/dev/null
# find world-writable files
$ find / -perm -o+w -type f 2>/dev/null
sudo & Processes
✓ Always use visudo to edit sudoers
✓ One file per user in sudoers.d/
✓ Specify full command paths in sudoers
✓ Use NOPASSWD only for automation
✓ Run jobs with nice to be kind to the system
✓ Use tmux for all remote long-running jobs
✗ Never NOPASSWD: ALL for humans
✗ Never use kill -9 as first resort
Audit sudo:
grep sudo /var/log/auth.log
Every sudo command is logged with timestamp, user, and full command.

Slide 18 — Summary

Key Takeaways

Every user is an identity. Use groups to manage collective permissions. Never assign rights to individuals one by one — that doesn't scale and is error-prone.

chmod is binary. When you need different access levels for different groups on the same resource, ACLs with setfacl/getfacl are the right tool.

Least privilege is a mindset. sudo entries should be as specific as possible — one command, one path, not full root. Compromise is contained by narrow access.

tmux is insurance. Develop the habit of running anything long-running inside a tmux session on remote servers — it takes 5 seconds to set up.

Commands you must know
useraddusermoduserdelgroupadd chmodchownchgrpumask setfaclgetfacl visudosudogpasswd pskillpkillnicerenice tmuxnohupjobsfgbg
Common mistakes to avoid:
• chmod 777 — never in production
• usermod -G without -a — silently removes other groups
• Editing /etc/sudoers directly — always use visudo
• Running long remote jobs without tmux
• Using SIGKILL before trying SIGTERM
• Giving humans NOPASSWD: ALL in sudoers
