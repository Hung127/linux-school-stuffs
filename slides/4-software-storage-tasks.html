Slide 3 — Theory

apt & dpkg — Package Management

# update package index
$ apt update
$ apt upgrade # upgrade all
$ apt full-upgrade # + remove old deps
# install / remove
$ apt install nginx
$ apt remove nginx # keep config
$ apt purge nginx # remove config too
$ apt autoremove # clean orphans
# search and inspect
$ apt search nginx
$ apt show nginx
$ dpkg -l # list all installed
$ dpkg -L nginx # list package files
apt vs dpkg: apt handles dependencies automatically. dpkg is the lower-level tool — use it to install .deb files directly or inspect installed packages.
Version pinning — never accidentally upgrade
# pin nginx to current version
$ apt-mark hold nginx
# verify
$ apt-mark showhold
nginx
# unpin when ready to upgrade
$ apt-mark unhold nginx
# install specific version
$ apt install nginx=1.24.0-1
Production rule: Always pin critical services (nginx, postgresql, docker) before running apt upgrade. Unplanned upgrades break things.
Slide 4 — Theory

apt & dpkg — Repair, Inspect, Pin

Repair a broken package state
# an install got interrupted? finish it
$ dpkg --configure -a
# unmet dependencies
$ apt --fix-broken install # = apt -f install
# force a clean reinstall
$ apt install --reinstall nginx
# roll back to an exact version
$ apt install nginx=1.24.0-1ubuntu1
Inspect — who needs what
$ apt-cache policy nginx # versions + source
$ apt-cache depends nginx # what it needs
$ apt-cache rdepends nginx # who needs it
$ dpkg -S /usr/sbin/nginx # which pkg owns a file
Priority pinning — /etc/apt/preferences.d/
# /etc/apt/preferences.d/nginx.pref
Package: nginx*
Pin: origin "nginx.org"
Pin-Priority: 1001
Priority guide: <100 never auto-installed · 500 default · 990 target release · >1000 allows a downgrade. Always confirm the result with apt-cache policy.
Reclaim disk + auto security patches
$ apt clean # wipe /var/cache/apt
$ apt autoremove --purge # drop orphans+config
$ apt install unattended-upgrades
$ dpkg-reconfigure unattended-upgrades
Tip: packages on apt-mark hold are skipped by unattended-upgrades too — pin critical services and they stay put automatically.
Slide 5 — Theory

PPAs & Build from Source

PPA — Personal Package Archive
# add a PPA (e.g. newer PHP)
$ add-apt-repository ppa:ondrej/php
$ apt update
$ apt install php8.3
# remove a PPA
$ add-apt-repository --remove ppa:ondrej/php
# manual source entry
# /etc/apt/sources.list.d/nginx.list:
deb https://nginx.org/packages/ubuntu jammy nginx
Trust PPAs carefully. Adding a PPA grants that maintainer the ability to push packages to your system. Use official or well-known PPAs only.
Build from source — the classic way
# install build tools first
$ apt install build-essential
# download + extract source
$ wget https://example.com/app-1.0.tar.gz
$ tar xzf app-1.0.tar.gz
$ cd app-1.0/
# configure → compile → install
$ ./configure --prefix=/usr/local
$ make -j$(nproc)
$ sudo make install
./configure checks system dependencies and generates a Makefile. Always check ./configure --help for available options before building.
Slide 6 — Theory

Signing Keys & snap / flatpak

Modern repo keys — apt-key is deprecated
# download + dearmor the signing key
$ curl -fsSL https://nginx.org/keys/nginx_signing.key \
    | gpg --dearmor \
    | sudo tee /etc/apt/keyrings/nginx.gpg >/dev/null
# bind the key to ONE repo via signed-by
# /etc/apt/sources.list.d/nginx.list
deb [signed-by=/etc/apt/keyrings/nginx.gpg] \
    https://nginx.org/packages/ubuntu jammy nginx
$ apt update
Why signed-by matters: a key in the global trust store can sign any package from any repo. signed-by scopes trust to a single source — a compromised third-party repo can't impersonate Ubuntu's.
snap & flatpak — beyond apt
# snap — ships with Ubuntu, auto-updates
$ snap install node --classic
$ snap list ; snap refresh
$ snap revert node # undo a bad update
# flatpak — sandboxed desktop apps
$ flatpak install flathub org.gimp.GIMP
$ flatpak run org.gimp.GIMP
Which one when?

Slide 7 — Theory

Partitions, Format & Mount

# inspect disks
$ lsblk # tree view
$ fdisk -l # partition table
$ df -h # disk usage
# partition a new disk
$ fdisk /dev/sdb # interactive
# n → new partition
# w → write and exit
# format
$ mkfs.ext4 /dev/sdb1
$ mkfs.xfs /dev/sdb1
# mount manually
$ mkdir -p /mnt/data
$ mount /dev/sdb1 /mnt/data
$ umount /mnt/data
/etc/fstab — persistent mounts
# device mountpoint fs options dump pass
/dev/sdb1 /mnt/data ext4 defaults,nofail 0 2
UUID=abc-123 /opt/logs xfs defaults 0 2
# get UUID (use instead of /dev path)
$ blkid /dev/sdb1
# test fstab before reboot!
$ mount -a
Use UUID, not /dev/sdX. Device names can change on reboot. UUIDs are stable. Always test with mount -a before rebooting.
Slide 8 — Theory

GPT, parted & Swap

GPT with parted — the modern default
$ parted /dev/sdb
(parted) mklabel gpt # GPT: >2TB, 128 parts
(parted) mkpart data ext4 0% 100%
(parted) print
(parted) quit
$ partprobe /dev/sdb # reload table, no reboot
# gdisk = an fdisk that speaks GPT
MBR vs GPT: MBR caps at 2 TB and 4 primary partitions. Use GPT for any large or new disk — and UEFI systems require it.
Add swap — a file is the flexible choice
$ fallocate -l 2G /swapfile
$ chmod 600 /swapfile # holds memory — lock it down
$ mkswap /swapfile
$ swapon /swapfile
$ swapon --show ; free -h
# persist in /etc/fstab:
/swapfile none swap sw 0 0
Mount options worth knowing
noatimeSkip access-time writes — faster, less SSD wear
nofailBoot continues if the device is missing
roRead-only mount
nosuid,nodevHarden a data-only disk
discardOnline TRIM for SSDs

LVM — Logical Volume Manager

The 3-layer stack
LOGICAL VOLUMES (what you use)
lv-root
20GB
lv-var
40GB
lv-data
80GB
↕
VOLUME GROUP (pool)
vg-main — 200GB total
↕
PHYSICAL VOLUMES (real disks)
/dev/sdb
100GB
/dev/sdc
100GB
↕
Physical Disk
Physical Disk
# 1. create physical volume
$ pvcreate /dev/sdb
$ pvdisplay
# 2. create volume group
$ vgcreate vg-main /dev/sdb
$ vgdisplay
# 3. create logical volume (40GB)
$ lvcreate -L 40G -n lv-data vg-main
# 4. format and mount
$ mkfs.ext4 /dev/vg-main/lv-data
$ mount /dev/vg-main/lv-data /opt/data
Think of LVM as virtual partitions. PV = physical disk, VG = a pool of storage, LV = the "partition" you actually use. Resize without rebooting.
Slide 10 — Theory

LVM — Online Resize

# scenario: /var is running out of space
$ df -h /var
Filesystem Size Used Avail Use%
/dev/vg-main/lv-var 40G 38G 1.2G 97%
# check available space in VG
$ vgdisplay vg-main | grep Free
Free PE / Size 1280 / 5.00 GiB
# extend by 5GB — NO UMOUNT NEEDED
$ lvextend -L +5G /dev/vg-main/lv-var
# resize filesystem to fill new space
$ resize2fs /dev/vg-main/lv-var # ext4
# or: xfs_growfs /var # xfs
# verify
$ df -h /var
/dev/vg-main/lv-var 45G 38G 6.2G 86%
Traditional disk vs LVM
OperationTraditionalLVM
Grow partition Unmount + tools Online, no umount
Span 2 disks RAID or impossible vgextend + lvextend
Snapshot Not available lvcreate --snapshot
Move data Manual copy pvmove (live)
Add a new disk to existing VG
# hot-add new disk /dev/sdc
$ pvcreate /dev/sdc
$ vgextend vg-main /dev/sdc
# VG now has more free space
# extend any LV as needed
Slide 11 — Theory

LVM — Snapshots & Shrink

Snapshot — an instant safety net
# freeze state before a risky migration
$ lvcreate -L 5G -s -n data-snap \
    /dev/vg-main/lv-data
# ...run the risky upgrade...
# A) roll back to the snapshot
$ lvconvert --merge /dev/vg-main/data-snap
# B) all good — drop the snapshot
$ lvremove /dev/vg-main/data-snap
DB backup pattern: snapshot → mount the snapshot read-only → back that up → remove it. The live database never pauses, and you get a consistent point-in-time copy.
Shrink — offline, and order is everything
# ext4: shrink the FILESYSTEM first, THEN the LV
$ umount /opt/data
$ e2fsck -f /dev/vg-main/lv-data
$ resize2fs /dev/vg-main/lv-data 30G
$ lvreduce -L 30G /dev/vg-main/lv-data
$ mount /opt/data
# XFS cannot shrink — grow-only
Reduce the LV below the filesystem and you lose data. Growing is the reverse order (lvextend → resize2fs) — which is why -r automates growth but is never safe for shrink.
Tear it all down
$ umount /opt/data ; lvremove /dev/vg-main/lv-data
$ vgremove vg-main ; pvremove /dev/sdb /dev/sdc

Slide 13 — Theory

Cron — Gotchas & Debugging

Why it works in your shell but not in cron

Cron runs with a near-empty environment — a minimal PATH and no profile sourced. This is the single most common cron bug.

# set the environment at the TOP of the crontab
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
MAILTO=admin@example.com # mail all output
# ALWAYS use absolute paths in the job
0 2 * * * /usr/bin/python3 /opt/job.py
# % means newline in cron — escape it!
0 0 * * * tar czf /bak/db-$(date +\%F).tgz /data
The % trap: an unescaped % silently truncates the command at that point. Always write \% inside cron lines.
Capture output & stop overlap
# log stdout AND stderr together
*/5 * * * * /opt/sync.sh >> /var/log/sync.log 2>&1
# never let two runs overlap
*/5 * * * * flock -n /tmp/sync.lock /opt/sync.sh
# silence success, still mail errors
0 * * * * /opt/job.sh > /dev/null
Where did my job go?
$ grep CRON /var/log/syslog
$ journalctl -u cron --since today
$ systemctl status cron # is it even running?
anacron runs jobs that were missed while the machine was off (laptops, dev boxes). Plain cron just skips them — use anacron or a systemd timer with Persistent=true.
Slide 14 — Theory

systemd timer — Modern Scheduling

Two unit files needed
# /etc/systemd/system/backup.service
[Unit]
Description=Daily backup job
[Service]
Type=oneshot
ExecStart=/opt/backup.sh
User=backup
# /etc/systemd/system/backup.timer
[Unit]
Description=Run backup daily
[Timer]
OnCalendar=*-*-* 02:00:00 # daily 2am
Persistent=true # catch missed
[Install]
WantedBy=timers.target
# enable and start the timer
$ systemctl daemon-reload
$ systemctl enable --now backup.timer
# list all active timers
$ systemctl list-timers
# check logs — this is the big advantage
$ journalctl -u backup.service
$ journalctl -u backup.service --since "1 week ago"
# run manually to test
$ systemctl start backup.service
cron vs systemd timer

LoggingManual/syslogjournalctl built-in
Missed runsSilently skippedPersistent=true
DependenciesNoneAfter=, Wants=
SyntaxSimplerMore verbose
Slide 15 — Theory

systemd timer — OnCalendar & Monotonic

OnCalendar syntax — and how to test it
# format: DOW YYYY-MM-DD HH:MM:SS (* = any)
OnCalendar=Mon *-*-* 09:00:00 # Mondays 09:00
OnCalendar=*-*-01 00:00:00 # 1st of month
OnCalendar=*-*-* *:0/15:00 # every 15 min
OnCalendar=daily # shorthand
# VALIDATE before you trust it:
$ systemd-analyze calendar "Mon *-*-* 09:00:00"
Next elapse: Mon 2026-06-08 09:00:00 ...
Shorthands: minutely · hourly · daily · weekly · monthly — each expands to a full OnCalendar expression.
Monotonic timers — relative to events
[Timer]
OnBootSec=15min # 15m after boot
OnUnitActiveSec=1h # then hourly after
RandomizedDelaySec=5m # jitter
AccuracySec=1min # coalescing window
Make it robust
Persistent=true # run missed jobs after downtime
# alert on failure — in the .service:
[Unit]
OnFailure=notify-admin@%n.service
$ systemctl list-timers --all
Fleet killer feature: 500 servers with the same 02:00:00 cron line all hit your backup host at once. RandomizedDelaySec spreads the load automatically.
Slide 16 — Real-world example

Example: /var full → expand online

Scenario — 3am alert: /var at 97%

Without LVM, you'd need to: schedule downtime, boot from live CD, resize partition, fsck, reboot. With LVM — zero downtime.

1 Alert fires: /var at 97% capacity
2 Check: VG has 5GB free → vgdisplay
3 lvextend -L +5G while /var is mounted
4 resize2fs to fill the new space
5 /var is now 45GB — no downtime, zero restarts
# full flow — under 2 minutes
$ df -h /var
/dev/vg-main/lv-var 40G 38.8G 774M 98% /var
$ vgs vg-main
VG #PV #LV VFree
vg-main 2 4 5.00g
$ lvextend -L +5G /dev/vg-main/lv-var
Logical volume lv-var successfully resized
$ resize2fs /dev/vg-main/lv-var
Filesystem on lv-var is now 11796480 (4k) blocks
$ df -h /var
/dev/vg-main/lv-var 45G 38.8G 5.2G 88% /var
Shortcut: lvextend -r -L +5G — the -r flag runs resize2fs automatically. One command does both steps.

Version pinning nginx on production

Your app relies on nginx 1.24 behavior. A junior admin runs apt upgrade and nginx jumps to 1.26 — breaking a rewrite rule.

Cron ran your backup script — did it succeed? With cron you check a log file manually. With systemd timer:

# exact status of last run
$ systemctl status backup.service
Active: inactive (dead)

$ journalctl -u backup.service -n 30

$ systemctl list-timers backup.timer

Slide 20 — Summary

Key Takeaways

Pin before you upgrade. Version holds are free. Unplanned package upgrades in production are not. Make pinning a default habit for critical services.

LVM is the standard. Any server that might need more disk space should use LVM. Resizing online is the difference between a 2-minute fix and a maintenance window.

UUID in fstab, always. /dev/sdb can become /dev/sdc after a reboot. UUIDs never change. A bad fstab entry can prevent boot.

systemd timer for new work. When writing new scheduled tasks, prefer systemd timers. journalctl integration makes debugging 10x easier than reading syslog.

Commands to memorize
apt-mark hold apt show dpkg -L apt-cache policy lvcreate lvextend -r lvcreate -s lvreduce vgdisplay resize2fs lsblk blkid parted mount -a crontab -e flock systemctl list-timers systemd-analyze calendar journalctl -u
4 things that break systems:
1. apt upgrade without pinning critical services
2. /dev/sdX in fstab instead of UUID
3. No mount -a test before reboot
4. Cron output going to /dev/null — errors silently lost
5. lvreduce before shrinking the filesystem — instant data loss
