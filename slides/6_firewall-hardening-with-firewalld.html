Why harden

A new server is an open door

Within minutes of getting a public IP, a server is scanned and probed. The defaults assume convenience, not safety.

  • Open by default. Services bind to all interfaces; nothing filters who reaches them.
  • root over SSH. The most-guessed username, on the most-attacked port (22).
  • No record. If something is touched, nothing is watching or logging it.
auth.log — minutes after boot
# Failed password for root from 45.x.x.x port 51244 # Failed password for root from 193.x.x.x port 40021 # Failed password for admin from 61.x.x.x port 33910 # Invalid user test from 110.x.x.x ...thousands per day, fully automated.
The fix is not one tool — it's layers

UFW Layer 01 · Network filtering

The uncomplicated firewall

UFW is a friendly front-end to the kernel's iptables/nftables. You write intent; it generates the rules.

  • Default-deny inbound. Block everything in, allow only what you name.
  • Allow outbound. Let the server reach out (updates, DNS).
  • Stateful. Replies to your own connections come back automatically.
Allow SSH before you enable. On a remote box, ufw enable with no allow 22 drops your own session instantly — and you can't reconnect. Always ufw allow 22/tcp first, then enable.
set the baseline policy
$ sudo ufw default deny incoming $ sudo ufw default allow outgoing $ sudo ufw enable Firewall is active and enabled on system startup $ sudo ufw status verbose Status: active Default: deny (incoming), allow (outgoing)
Start closed. Open deliberately.
UFW allow · deny

Opening exactly what you need

rules
# by port + protocol $ sudo ufw allow 22/tcp $ sudo ufw allow 80,443/tcp # by service name (uses /etc/services) $ sudo ufw allow https # scope to a source — admin subnet only $ sudo ufw allow from 10.0.0.0/24 to any port 22 # explicitly block a legacy port $ sudo ufw deny 23 # telnet

allow vs deny vs reject

allow let the packet through.
deny drop silently — attacker sees a timeout.
reject refuse with a reply — sender learns the port is closed.

Order & specificity: a narrow allow from beats a broad rule. UFW evaluates rules top-to-bottom — list with ufw status numbered, insert with ufw insert N.
Every open port is a promise you have to keep
UFW limit · logging

Rate-limit and watch

limit — throttle abuse

ufw limit ssh allows SSH but blocks a source IP that makes 6+ connections in 30 seconds — a cheap brake on brute-force before fail2ban even reacts.

logging — leave a trail

Levels: off → low → medium → high → full. Logs land in /var/log/ufw.log. Use medium in the labs; full is noisy.

limit + logging
$ sudo ufw limit 22/tcp $ sudo ufw logging medium $ sudo tail -f /var/log/ufw.log [UFW BLOCK] SRC=203.0.113.9 DPT=3306 [UFW BLOCK] SRC=198.51.100.4 DPT=23 [UFW LIMIT BLOCK] SRC=45.0.0.7 DPT=22
limit = first speed bump · logging = the camera
firewalld Red Hat · Layer 01 · Network filtering

firewalld — the Red Hat firewall

RHEL / Rocky / Alma / Fedora ship firewalld, not UFW. Same job as UFW — a friendly front-end to nftables — but organised around zones.

  • A zone is a trust level. Each network interface is assigned to one zone; the zone decides what's allowed.
  • public is the default. Deny-by-default inbound; only SSH and a few services pre-opened.
  • Other built-ins: trusted (allow all), internal, dmz, drop (silent deny), block (reject).
Mental shift from UFW: UFW keeps one flat rule list. firewalld groups rules by zone, so the same laptop can trust its home LAN and distrust airport Wi-Fi — just by switching the interface's zone.
inspect zones
$ sudo firewall-cmd --state running $ sudo firewall-cmd --get-default-zone public $ sudo firewall-cmd --list-all public (active) interfaces: eth0 services: ssh dhcpv6-client ports: target: default # = deny inbound
A zone is "how much do I trust this network?"
firewalld service · port · --permanent

Opening exactly what you need

rules
# prefer named services over raw ports $ sudo firewall-cmd --add-service=https $ sudo firewall-cmd --add-service=http # a raw port when no service name exists $ sudo firewall-cmd --add-port=8080/tcp # the TWO-STEP that everyone forgets: # 1) make it survive reboot 2) load it now $ sudo firewall-cmd --permanent --add-service=https $ sudo firewall-cmd --reload # remove a rule $ sudo firewall-cmd --permanent --remove-service=http
The #1 firewalld gotcha — runtime vs permanent. A plain --add-service is runtime only and vanishes on reboot. For a lasting rule you must add --permanent and then --reload. Forgetting either is the classic "it worked, then it didn't after reboot".

Rich rules — scope & rate-limit

Fine-grained control, firewalld's answer to ufw allow from + ufw limit:

# only the admin subnet may reach SSH $ sudo firewall-cmd --permanent \ --add-rich-rule='rule family=ipv4 \ source address=10.0.0.0/24 \ service name=ssh accept' # throttle SSH: max 6 new conns / minute $ ... service name=ssh \ limit value=6/m accept
--permanent writes the file · --reload applies it
firewalld zones in practice

Two cables, two trust levels

A database server has two NICs: eth0 faces the Internet, eth1 faces the private app network. You want SSH + HTTPS from outside, but the Postgres port only from inside.

assign interfaces to zones
# public NIC → public zone (SSH, HTTPS only) $ sudo firewall-cmd --permanent \ --zone=public --change-interface=eth0 $ sudo firewall-cmd --permanent \ --zone=public --add-service=https # private NIC → internal zone (+ Postgres) $ sudo firewall-cmd --permanent \ --zone=internal --change-interface=eth1 $ sudo firewall-cmd --permanent \ --zone=internal --add-port=5432/tcp $ sudo firewall-cmd --reload

Why this beats a flat rule list

Port 5432 is reachable only on the internal NIC. An attacker on the public interface can't even see the database port — it isn't "blocked", it simply doesn't exist in that zone.

UFW equivalent? You'd write per-source rules like ufw allow from 10.0.0.0/24 to any port 5432. It works, but zones make the intent explicit: "this cable is trusted, that one isn't."
Zones model the network's shape, not just its ports

Pick by distro, not preference. Don't install UFW on RHEL or firewalld on Ubuntu — fighting the platform's default creates confusing double-firewall states. Learn both dialects; the grammar (deny-by-default, open deliberately, scope narrowly) is identical.
One firewall philosophy, two command sets
iptables underneath UFW

The three chains

ChainHandles
INPUTPackets destined for this host (incoming to a local service)
OUTPUTPackets generated by this host (outgoing)
FORWARDPackets passing through — routing/gateway traffic
Tables & targets. Default table is filter. Common targets: ACCEPT DROP REJECT. UFW writes its rules into these very chains.
raw rules
# default-drop INPUT, then open SSH # iptables -P INPUT DROP # iptables -A INPUT -i lo -j ACCEPT # iptables -A INPUT -m state \ --state ESTABLISHED,RELATED -j ACCEPT # iptables -A INPUT -p tcp \ --dport 22 -j ACCEPT # iptables -L INPUT -n -v --line-numbers
UFW is the steering wheel — iptables is the engine
iptables NAT basics

Rewriting addresses with NAT

nat chainWhen it runs
PREROUTINGRight after arrival — used for DNAT (port forwarding)
POSTROUTINGJust before leaving — used for SNAT / MASQUERADE
  • MASQUERADE shares one public IP with a private network (a gateway).
  • DNAT forwards an external port to an internal host.
gateway NAT
# LAN behind one public IP (eth0 = WAN) # iptables -t nat -A POSTROUTING \ -o eth0 -j MASQUERADE # forward public :8080 -> internal web # iptables -t nat -A PREROUTING \ -p tcp --dport 8080 \ -j DNAT --to 192.168.1.10:80 # sysctl -w net.ipv4.ip_forward=1
NAT moves packets; firewall rules still decide if they're allowed
fail2ban Layer 04 · Active defense

Ban the attacker, not just the packet

fail2ban reads your logs, matches failure patterns, and tells the firewall to block the offending IP — automatically, for a while.

  • Jail = a watched log + the rules for acting on it.
  • Filter = the regex that recognizes a failed attempt.
  • Action = what to do on a match (usually add a firewall ban).
the loop
log line → filter regex → count ↓ (maxretry reached within findtime) action: iptables DROP this IP ↓ (bantime elapses) unban automatically # watches auth.log for "Failed password"
Turns a flood of guesses into a single short-lived block
fail2ban jail.local · filters · actions

Configuring an SSH jail

/etc/fail2ban/jail.local
# never edit jail.conf — override here [sshd] enabled = true port = 22 maxretry = 5 # strikes findtime = 10m # window bantime = 1h # -1 = forever backend = systemd

Where the pieces live

Filters: /etc/fail2ban/filter.d/sshd.conf — the failregex patterns.
Actions: /etc/fail2ban/action.d/ — e.g. iptables-multiport.

check & manage
$ sudo fail2ban-client status sshd Currently banned: 3 Banned IP list: 45.0.0.7 ... $ sudo fail2ban-client set sshd \ unbanip 45.0.0.7
Edit jail.local, restart, then verify with the client
SSH Layer 02 · Service exposure

Harden the front door

/etc/ssh/sshd_config
PermitRootLogin no Port 2222 AllowUsers deploy mmt PasswordAuthentication no PubkeyAuthentication yes MaxAuthTries 3 $ sudo sshd -t # test config $ sudo systemctl restart ssh
  • Disable root login. Force a named user + sudo — attributable and harder to guess.
  • Change the port. Cuts noise from automated scanners (obscurity, not security).
  • AllowUsers. An allow-list of who may even attempt SSH.
  • Keys over passwords. Removes guessable secrets entirely.
Don't lock yourself out. Open the new port in the firewall first, and keep your current session open while you test a new login in a second terminal.
Validate with sshd -t before every restart
PAM Layer 03 · Authentication

Policy where logins happen

Password quality — pam_pwquality

In /etc/security/pwquality.conf: minlen=12, dcredit / ucredit / ocredit to require digits, uppercase, symbols.

Lockouts — pam_faillock

Lock an account after repeated failures: deny=5 unlock_time=900. Inspect with faillock --user mmt.

Login limits — limits.conf

/etc/security/limits.conf caps sessions & resources, e.g. @students hard maxlogins 2.

pwquality.conf
minlen = 12 dcredit = -1 # ≥1 digit ucredit = -1 # ≥1 uppercase ocredit = -1 # ≥1 symbol retry = 3 $ faillock --user mmt mmt: When Type Source Valid
PAM = the rulebook every service consults to let you in
auditd Layer 05 · Audit

Watching the crown-jewel files

The Linux Audit daemon records who touched what, when. Put watches on the files that define identity on the box.

  • -w path watch a file or directory.
  • -p rwxa which access types: read, write, exec, attribute change.
  • -k key a label to search by later.
Make it persistent: put rules in /etc/audit/rules.d/hardening.rules so they survive reboot.
watch + search
# auditctl -w /etc/passwd -p wa -k identity # auditctl -w /etc/shadow -p rwa -k identity # later — who touched it? # ausearch -k identity -i type=PATH name="/etc/shadow" uid=1000 auid=1000 comm="cat" # aureport -f -i | tail
You can't investigate what you never recorded
Logs journalctl · auth.log

Reading the security record

journalctl
# follow the SSH service live $ journalctl -u ssh -f # auth events since boot, errors only $ journalctl _SYSTEMD_UNIT=ssh.service \ --since today -p err # classic text log (Debian/Ubuntu) $ grep "Failed password" \ /var/log/auth.log | wc -l 1843
Look forMeans
Failed passwordA rejected login — count spikes = brute-force
Accepted publickeyA successful key-based login (good)
Invalid userLogin for a non-existent account — pure probing
sudo: ... COMMANDPrivilege escalation — who ran what as root
journald vs files: systemd's journal is structured and filterable; auth.log is plain text that's easy to grep. Use both.
The logs already hold the story — learn to ask them
Lynis automated audit

Score your hardening

Lynis scans the running system, checks hundreds of settings, and produces a hardening index plus prioritized findings.

  • [WARNING] fix these — real gaps.
  • [SUGGESTION] nice-to-have improvements.
  • Hardening index 0–100 track it over time, not as an absolute grade.
Reports: /var/log/lynis.log (full) and /var/log/lynis-report.dat (machine-readable).
lynis audit system
$ sudo lynis audit system [+] SSH Support [WARNING] Root login allowed (SSH-7412) [SUGGESTION] Set MaxAuthTries to 3 Hardening index : [ 63 / 100 ] Tests performed : 264 See /var/log/lynis.log for details
Audit → fix the warnings → re-audit → watch the index climb
Case study 1

The clinic server under attack

A small Vietnamese clinic runs its patient-record app on a Linux VPS. Defaults left in place: root SSH on port 22, password login, no monitoring.

LayerWhat it would have done
01 UFWClosed everything except 443 — the bot never reaches 22
02 SSHNo root login, non-standard port — guesses fail outright
04 fail2banBans the source IP after 5 tries
05 auditdRecords any access to /etc/shadow for the incident report

Timeline

00:00 — VPS gets a public IP.
00:04 — first scan hits port 22.
00:30 — ~2,000 root password guesses logged.
02:00 — weak password cracked; attacker reads patient data.

Lesson: any single layer would have broken this chain. With none, the breach was a matter of hours — and a reportable disclosure of health data.
Defense in depth turns "hours to breach" into "never reached"
Case study 2

Locked out by good intentions

An admin hardens SSH correctly — but in the wrong order — and loses all access to a remote machine.

what went wrong
# changed port to 2222 and restarted... $ sudo systemctl restart ssh # ...but firewall still only allows 22 $ ssh -p 2222 mmt@server ssh: connect ... Connection refused

The safe sequence

1. Open the new port in UFW first.
2. sshd -t to validate config.
3. Restart SSH.
4. Test the new login in a second terminal — keep the first one open.
5. Only then close the old port.

Lesson: hardening is a sequence, not a switch. Always keep an escape hatch (an open session, console access) until the new path is proven.
Security changes fail safe only if you order them safely
Case study 3 firewalld

The rule that vanished at 3 a.m.

A junior admin on a Rocky Linux box opens a new API port during an incident. It works. A routine reboot that night takes the API offline — and no one knows why.

what happened
# during the incident — runtime only! $ sudo firewall-cmd --add-port=9443/tcp success # API reachable, everyone relaxes # 02:00 — scheduled reboot # runtime rules are gone; only --permanent survives $ curl https://api.internal:9443 curl: (7) Failed to connect — refused

The fix & the habit

1. Add runtime rule to test fast.
2. Once confirmed, re-add it --permanent.
3. --reload and verify with --list-all.
4. Or capture current runtime into permanent in one shot:
firewall-cmd --runtime-to-permanent.

Lesson: on firewalld, "it works now" and "it survives reboot" are two separate states. The runtime/permanent split is powerful for safe testing — but only if every proven rule is written back to permanent before you walk away.
Runtime is a draft · permanent is the saved file

Lab 1 UFW · 22 / 80 / 443

Lock the firewall down

1
Set default-deny policy
$ sudo ufw default deny incoming $ sudo ufw default allow outgoing
2
Allow exactly the three ports
$ sudo ufw allow 22/tcp $ sudo ufw allow 80,443/tcp
3
Enable & verify
$ sudo ufw enable $ sudo ufw status numbered

Prove it works

From the attacker VM, scan the target:

$ nmap -p 22,80,443,3306,23 target 22/tcp open 80/tcp open 443/tcp open 3306/tcp filtered 23/tcp filtered
On Red Hat? Do the same with firewalld: firewall-cmd --permanent --add-service={ssh,http,https} then --reload. Verify with firewall-cmd --list-all — the nmap result is identical.
Deliverable: a screenshot of the status output (ufw status numbered or firewall-cmd --list-all) and the nmap result showing only 22/80/443 open.
filtered = the firewall dropped it silently
Lab 2 fail2ban · brute-force

Trip the trap, confirm the ban

1
Install & enable
$ sudo apt install fail2ban -y $ sudo systemctl enable --now fail2ban
2
Configure a strict sshd jail

In /etc/fail2ban/jail.local: maxretry=3, findtime=5m, bantime=10m, then restart.

3
Simulate the attack

From the attacker VM, fail SSH on purpose several times:

$ for i in 1 2 3 4; do \ ssh wronguser@target; done

Confirm the ban

$ sudo fail2ban-client status sshd Currently failed: 0 Currently banned: 1 Banned IP list: 192.168.56.20 $ sudo iptables -L -n | grep .56.20 DROP all -- 192.168.56.20
Deliverable: the attacker IP in the banned list and the matching iptables DROP rule. Bonus: unban it with fail2ban-client set sshd unbanip.
The ban should appear after the 3rd failed attempt
Lab 3 auditd · passwd & shadow

Catch access to identity files

1
Install auditd
$ sudo apt install auditd -y $ sudo systemctl enable --now auditd
2
Add persistent watches

Append to /etc/audit/rules.d/identity.rules, then augenrules --load:

-w /etc/passwd -p wa -k identity -w /etc/shadow -p rwa -k identity
3
Trigger an event
$ sudo cat /etc/shadow > /dev/null

Find who did it

$ sudo ausearch -k identity -i | tail type=SYSCALL ... comm="cat" name="/etc/shadow" auid=1000 uid=0 success=yes
Deliverable: the ausearch output showing your read of /etc/shadow, with the auid (the human behind the action).
auid survives su/sudo — it ties the act back to the real user
Lab 4 Lynis · audit & remediate

Score, fix, re-score

1
Run the baseline audit
$ sudo apt install lynis -y $ sudo lynis audit system

Record the hardening index (e.g. 63/100).

2
Pick 3 HIGH warnings

From the report, choose three — likely: root SSH login, missing password policy, no firewall.

3
Remediate & re-run

Apply fixes (you built most in this lesson), then lynis audit system again and compare.

Example remediations

SSH-7412 → PermitRootLogin no
AUTH-9286 → set pwquality minlen/complexity
FIRE-4513 → enable UFW (Lab 1)

Deliverable: a short before/after table — index, the 3 warning IDs, what you changed, and the new index. The number should rise.
The goal isn't 100 — it's a measured, justified improvement
Wrap-up

What to carry forward

  • Start closed. Default-deny inbound; open only what a service truly needs.
  • No single layer suffices. Firewall, SSH, PAM, fail2ban, auditd each cover a different gap.
  • Order matters. Open the path before you close the old one — keep an escape hatch.
  • Measure it. Logs tell the story; Lynis turns posture into a number you can improve.

The five layers, one line each

01 UFW / iptables — filter packets
02 SSH config — shrink exposure
03 PAM — strengthen auth
04 fail2ban — ban attackers live
05 auditd / journalctl / Lynis — watch, record, score
