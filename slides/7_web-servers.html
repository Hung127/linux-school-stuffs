Part 1
Foundations

What a web server actually does before we touch a config file.

01Foundations

Web server vs. app server vs. reverse proxy

Web server

Speaks HTTP. Accepts requests, returns static files, or forwards to a backend. Apache, Nginx.

Application server

Runs your program that generates responses. PHP-FPM, Gunicorn, Node, Tomcat.

Reverse proxy

Sits in front, terminates TLS, load-balances, caches, routes to backends. Often the same Apache/Nginx process.

One box can be all three at once. Apache serves static assets, terminates TLS, and proxies /api to PHP-FPM — simultaneously.

02Foundations

The HTTP request/response cycle

Client→ TCP connect :443→ Request line + headers→ Server routes→ Response + body
request
GET /index.html HTTP/1.1
Host: demo.hcmus.edu.vn
User-Agent: curl/8.6
Accept: text/html
response
HTTP/1.1 200 OK
Server: Apache
Content-Type: text/html
Content-Length: 348
<!-- body follows -->

Recap targets: methods (GET/POST/PUT/DELETE), status classes (2xx/3xx/4xx/5xx), key headers (Host, Content-Type, Cache-Control).

03Foundations

How a server "listens": the socket lifecycle

socket() create endpoint
bind() claim :80 / :443
listen() queue connections
accept() one per client
read/write the HTTP exchange
close() or keep-alive

Ports below 1024 are privileged — that's why httpd starts as root, binds :80/:443, then drops privileges to the apache user.

who is listening?
[root@centos ~]# ss -tlnp | grep httpd
LISTEN 0 511 *:80    users:(("httpd"...))
LISTEN 0 511 *:443   users:(("httpd"...))

04Foundations

Static vs. dynamic content

Static

File read straight from disk: HTML, CSS, JS, images. Fast, cacheable, no code runs. Apache handles this natively and extremely well.

DocumentRoot → file

Dynamic

Response is generated per request by a program. Apache hands the request off to a backend (PHP-FPM, WSGI, Node) and relays the result.

DocumentRoot → app → response

Rule of thumb: serve static from the web server, generate dynamic in an app server. Mixing them is where most misconfigurations (and vulnerabilities) live.

Part 2
The Linux environment

Where httpd lives on a CentOS box, and who it runs as.

05Linux env

httpd in the process model

  • A web server is a daemon — a long-running background process.
  • On CentOS it is managed by systemd as the httpd.service unit.
  • A parent process runs as root to bind privileged ports, then spawns worker children as the apache user.
  • systemd handles start on boot, restart on crash, and log capture via journald.
process tree
[root@centos ~]# ps -ef | grep httpd
root   1201  ... httpd -DFOREGROUND
apache 1203  1201 httpd -DFOREGROUND
apache 1204  1201 httpd -DFOREGROUND
apache 1205  1201 httpd -DFOREGROUND
06Linux env

Run as apache, never as root

  • Workers run as the unprivileged apache user & group.
  • If a worker is compromised, the blast radius is limited to what apache can touch.
  • Content files should be owned by a deploy user, only readable by apache — not writable.

Anti-pattern: chmod 777 on the document root. Never do this to "make it work."

who am I
[root@centos ~]# grep -E '^User|^Group' \
   /etc/httpd/conf/httpd.conf
User apache
Group apache

[root@centos ~]# chown -R deploy:apache /var/www/site
[root@centos ~]# chmod -R 750 /var/www/site
07Linux env

Where everything lives on CentOS

httpd filesystem map
/etc/httpd/conf/httpd.conf          # main configuration
/etc/httpd/conf.d/*.conf            # drop-in configs (vhosts, ssl)
/etc/httpd/conf.modules.d/*.conf    # which modules load (incl. MPM)
/var/www/html/                     # default DocumentRoot
/var/log/httpd/access_log           # every request
/var/log/httpd/error_log            # diagnostics + startup errors
/usr/sbin/httpd                     # the binary (a.k.a. apachectl)

Debian/Ubuntu differ: there it's /etc/apache2, apache2 service, www-data user, and a2ensite. Know the difference when you switch distros.

Part 3
Apache httpd

Architecture, the module system, and getting it installed.

08Apache

The server landscape — and why Apache

Apache httpd

Process/thread model, huge module ecosystem, per-directory .htaccess overrides. Our example.

Nginx

Event-driven, excels as a reverse proxy and at high concurrency with low memory.

Caddy

Automatic HTTPS out of the box, simple config — great for quick deploys.

Embedded

Node, Gunicorn, Tomcat — app servers that also speak HTTP directly.

Pick Apache for its mature module system, .htaccess flexibility, and ubiquity on RHEL/CentOS. Pick Nginx when raw proxy throughput dominates.

09Apache

Apache architecture: MPMs & modules

Multi-Processing Modules decide how connections are handled:

  • prefork — one process per connectionsafe for non-thread-safe code (old mod_php), heavy on RAM
  • worker — threads inside processeslighter, needs thread-safe modules
  • event — worker + smart keep-alive handlingCentOS default; best for many idle connections
modules & MPM

mpm_event_module (shared)
ssl_module (shared)
proxy_module (shared)

Always test first

Part 5
Configuration

Virtual hosts, directories, MIME types, and directives that matter.

13Config

How the config is organized

  • httpd.conf — global defaults: User, Listen, DocumentRoot, log formats.
  • conf.d/*.conf — drop-in files; one per site or feature (auto-included).
  • Directives are containers and key-value lines. Containers scope settings.
/etc/httpd/conf/httpd.conf
Listen 80                          # global directive

<Directory "/var/www/html">          # container: scopes what's inside
    Options -Indexes +FollowSymLinks
    AllowOverride None
    Require all granted
</Directory>
▶ DEMOOpen /etc/httpd/conf/httpd.conf, find a <Directory> block, then apachectl configtest.
14Config

Virtual hosts: many sites, one server

Apache picks the vhost by matching the Host: header (name-based). One IP can serve dozens of domains.

  • ServerName — the domain to match
  • DocumentRoot — files for this site
  • Separate log files per site
/etc/httpd/conf.d/demo.conf
<VirtualHost *:80>
  ServerName  demo.hcmus.edu.vn
  DocumentRoot /var/www/demo
  ErrorLog  /var/log/httpd/demo_error.log
  CustomLog /var/log/httpd/demo_access.log combined
</VirtualHost>
▶ DEMOCreate /var/www/demo/index.html, write this vhost, reload, then curl -H "Host: demo.hcmus.edu.vn" localhost.
15Config

Directories, indexes & MIME types

  • DirectoryIndex — file served for / (index.html)
  • Options -Indexes — turn off auto directory listing
  • AllowOverride — whether .htaccess may override here
  • MIME types — map extensions to Content-Type via mod_mime

.htaccess

Per-directory overrides read on every request. Flexible for shared hosting, slower and riskier — disable with AllowOverride None when you control the main config.

Security: directory listing exposes files you never meant to publish. Keep -Indexes on.

/etc/httpd/conf.d/example.conf — a concrete block
<Directory "/var/www/demo">
  DirectoryIndex index.html index.php  # try these in order for /
  Options -Indexes              # no auto file listing
  AllowOverride None            # ignore .htaccess (faster, safer)
  Require all granted           # allow public access
</Directory>
AddType application/wasm .wasm   # MIME: map .wasm → correct Content-Type
▶ DEMO1. echo "<h1>hi</h1>" | sudo tee /var/www/demo/index.html → visit /, you get it (DirectoryIndex).  2. delete it, set Options +Indexes, reload → / shows a raw file listing.  3. back to -Indexes → 403 Forbidden.

16Dynamic

Serving dynamic content

CGI→ FastCGI→ PHP-FPM / app server
  • CGI — spawn a process per request. Simple, slow.
  • FastCGI — persistent worker pool. The modern way.
  • Apache reaches the backend over a unix socket or TCP.
inside the vhost · /etc/httpd/conf.d/demo.conf
<FilesMatch \.php$>
  SetHandler "proxy:unix:/run/php-fpm/www.sock|fcgi://localhost"
</FilesMatch>

17Dynamic

Reverse proxy: the components

Apache fronts any HTTP backend via mod_proxy — one public door, the backend hidden on localhost:

ProxyPass routes matching URLs · ProxyPassReverse rewrites the backend's redirects.

/etc/httpd/conf.d/demo.conf
<VirtualHost *:80>
  ServerName demo.hcmus.edu.vn
  # add these 3 lines inside the vhost:
  ProxyPreserveHost On
  ProxyPass        /api  http://127.0.0.1:3000/
  ProxyPassReverse /api  http://127.0.0.1:3000/
</VirtualHost>

Edit the vhost file, not httpd.conf. Enable modules first (usually already on): proxy, proxy_http; for balancing add proxy_balancer + a method module. Then apachectl configtest & reload.

▶ DEMOAdd the ProxyPass lines, reload, then curl localhost/api/ — answered by the backend on :3000.
18Dynamic

Load balancing a backend pool

/etc/httpd/conf.d/demo.conf (inside vhost)
<Proxy balancer://appcluster>
  BalancerMember http://127.0.0.1:3001
  BalancerMember http://127.0.0.1:3002
  BalancerMember http://127.0.0.1:3003
  ProxySet lbmethod=byrequests
</Proxy>

ProxyPass        /app  balancer://appcluster/
ProxyPassReverse /app  balancer://appcluster/

Scenario: requests to /app rotate across the healthy pool (:3001 → :3003). When :3002 fails its health check the balancer drops it automatically — no error reaches the user. Needs modules: proxy, proxy_http, proxy_balancer + a lbmethod_* module.

▶ DEMORun three Node instances on :3001–:3003, hit curl localhost/app/ repeatedly — responses rotate; kill one and watch traffic route around it.
Part 7
Performance, load & scale

One box is finite. Tune it, measure it, then scale it.

19Performance

Tuning workers, memory & KeepAlive

/etc/httpd/conf.modules.d/00-mpm.conf
<IfModule mpm_event_module>
  StartServers            2
  ServerLimit             16
  ThreadsPerChild         25
  MaxRequestWorkers      400   # concurrency ceiling
  MaxConnectionsPerChild 1000
</IfModule>

# httpd.conf
KeepAlive On
KeepAliveTimeout 5          # free idle workers fast
  • MaxRequestWorkers = concurrency ceiling; beyond it, requests queue.
  • RAM budget = workers × per-process RAM. Set the ceiling so the box never swaps.
  • prefork is RAM-hungry (1 process/conn); event is far lighter.
  • KeepAlive speeds repeat requests but ties up a worker — short timeout.

Where's the bottleneck? CPU (dynamic code / TLS) · RAM (too many processes) · I/O (logs, DB).

▶ DEMOChange MaxRequestWorkers, reload, fire load, and watch RAM/CPU move in htop.

22Performance

Scaling: vertical, horizontal & the session trap

  • Vertical — a bigger box (more CPU/RAM). Simple, but a hard ceiling and costly.
  • Horizontal — more boxes behind a load balancer (Nginx / HAProxy / Apache). Scales out.
  • The trap — user logs in on App A; the next request lands on App B → logged out.
  • Fixes — sticky sessions (pin user to one node) or a shared store (Redis / Memcached).

Prefer a shared store: sticky sessions unbalance the load and lose the session if that node dies.

Part 8
TLS / HTTPS

Certificates, redirects, and getting an A on the SSL test.

23TLS

What happens on https:// — port 80 vs 443

  • Type the bare domain → browser first hits :80 (HTTP).
  • Apache on :80 answers 301 → https:// — so :80 must stay open.
  • Browser retries on :443 → TLS handshake: ClientHello → ServerHello + Certificate → verify → session key.
  • From then on every byte is encrypted with that key.
  • HSTS — after the first visit the browser jumps straight to :443, skipping the risky :80 hop (stops SSL-stripping).

An HTTPS server listens on both 80 and 443. Kill :80 and users typing the bare domain get "can't connect".

▶ DEMOcurl -I http://demo... shows the 301; curl -Iv https://demo... shows the handshake + certificate.

Force HTTPS & set HSTS

/etc/httpd/conf.d/demo.conf (+ *-ssl.conf)
<VirtualHost *:80>
  ServerName demo.hcmus.edu.vn

  "max-age=31536000; includeSubDomains"
  • Redirect all plain HTTP to HTTPS with a 301.
  • HSTS tells the browser to never try HTTP again.
  • Disable old protocols: TLS 1.2+ only, no SSLv3.

27Logs

Common failure modes on CentOS

Permission denied

File not readable by apache, or blocked by SELinux context. Check both.

Address already in use

Another process holds :80. Find it with ss -tlnp.

configtest failed

Syntax error. Run apachectl configtest — it names the file and line.

Connection refused (remote)

Service up locally but firewalld blocks the port. Open http/https.

The pattern: works on curl localhost but not from outside → firewall or SELinux. Works for root but not apache → permissions or SELinux context.

Part 10
Hardening

Least privilege, quiet banners, safe headers, and SELinux.

28Security

Hardening the configuration

/etc/httpd/conf.d/hardening.conf
ServerTokens Prod        # hide version in headers
ServerSignature Off      # no banner on error pages
TraceEnable Off          # block TRACE method

<Directory />
  Options -Indexes         # no directory listing
  Require all denied      # deny by default
</Directory>
DirectiveWhat it does & why it matters
ServerTokens ProdTrims the Server: header to just Apache. Without it, httpd leaks its exact version + OS — a map for an attacker to look up known CVEs.
ServerSignature OffRemoves the version banner Apache prints at the bottom of its error pages (404/403). Same information leak, different place.
TraceEnable OffDisables the HTTP TRACE method, which can be abused (Cross-Site Tracing) to read cookies the browser normally hides.
<Directory />
Require all denied		Deny access to the whole filesystem by default; you then re-allow only your docroot. Stops a stray Alias from exposing /etc.

Put global tweaks in a drop-in file — create /etc/httpd/conf.d/hardening.conf (every *.conf there is auto-included) rather than editing /etc/httpd/conf/httpd.conf — easier to audit and it survives package updates.

▶ DEMO1. sudo vi /etc/httpd/conf.d/hardening.conf and add ServerTokens Prod  2. sudo apachectl configtest (expect Syntax OK)  3. sudo systemctl reload httpd  4. curl -I localhost → the Server: line now reads just Apache, no version.
29Security

Security headers — the app layer defense

  • CSP — blunts XSS
  • X-Frame-Options — blocks clickjacking
  • X-Content-Type-Options — stops MIME sniffing
  • SameSite cookies — mitigates CSRF

This is where the web-server config meets the vulnerability topics from our other labs — the server sets the guardrails the browser enforces.

vhost, or /etc/httpd/conf.d/security-headers.conf
Header always set X-Frame-Options "DENY"
Header always set X-Content-Type-Options "nosniff"
Header always set Content-Security-Policy \
  "default-src 'self'"
Header always set Referrer-Policy \
  "strict-origin-when-cross-origin"
▶ DEMOAdd X-Frame-Options DENY, reload, curl -I localhost — the header now shows up.
30Security

Content-Security-Policy in depth

vhost or /etc/httpd/conf.d/security-headers.conf
<IfModule mod_headers.c>
  Header set Content-Security-Policy "\
    default-src 'self'; \
    script-src 'self' https://analytics.example; \
    style-src 'self' 'unsafe-inline'; \
    frame-ancestors 'none'"
</IfModule>

# build the allowlist safely first (blocks nothing):
Header set Content-Security-Policy-Report-Only "default-src 'self'"
  • A response header saying which sources the browser may load — the browser enforces it.
  • Stops XSS: an injected <script src=evil> is blocked (not on the allowlist).
  • frame-ancestors 'none' blocks clickjacking (page can't be framed).
  • Report-Only logs violations but blocks nothing — roll it out first, find every legit source, then enforce.

Careful: too-strict CSP silently breaks the site (blocks legit CDNs/fonts). Verify in F12 → Network, or curl -I.

▶ DEMOcurl -I https://demo... | grep -i content-security — confirm the header ships; open F12 console to see a blocked script.
31Security

X-Frame-Options, nosniff & SameSite

vhost or /etc/httpd/conf.d/security-headers.conf
<IfModule mod_headers.c>
  Header always set X-Frame-Options "DENY"
  Header always set X-Content-Type-Options "nosniff"

  # tighten cookies (better: set these in the app)
  Header always edit Set-Cookie ^(.*)$ \
    "$1; SameSite=Lax; Secure; HttpOnly"
</IfModule>

X-Frame-Options: DENY

Page can't be loaded in an <iframe>. Blocks clickjacking — an attacker overlays your page invisibly and tricks the click. Modern form: CSP frame-ancestors.

X-Content-Type-Options: nosniff

Browser must trust the declared Content-Type, not guess. Blocks an uploaded avatar.jpg that hides HTML/JS from being run as a page — upload-based XSS.

Set-Cookie: SameSite=Lax

Cookie isn't sent on cross-site requests. Blocks CSRF — evil.com auto-submits a form to the bank using the victim's logged-in cookie. Pair with Secure + HttpOnly.

▶ DEMOAdd the three headers, reload, curl -I https://demo... — all three lines appear in the response.
32Security

nosniff: stopping upload-based XSS

Without nosniff — attack

  • 1 · Attacker uploads avatar.jpg that is actually JavaScript.
  • 2 · Server trusts the .jpg extension, stores it, serves Content-Type: image/jpeg.
  • 3 · Victim opens /uploads/avatar.jpg directly.
  • 4 · Browser sniffs the bytes, sees <script>, treats it as HTML and runs it → cookie stolen.

With nosniff — blocked

Browser is forced: "server said image/jpeg → handle it as an image, no guessing." The bytes aren't a valid image, so nothing renders and the hidden script never runs.

/etc/httpd/conf.d/security.conf
<IfModule mod_headers.c>
  Header set X-Content-Type-Options "nosniff"
</IfModule>
▶ DEMOVerify: curl -I https://demo... | grep -i x-content-type → nosniff. Then open the fake .jpg — it no longer executes.
33Security

SameSite cookies: stopping CSRF

Without SameSite — CSRF

  • 1 · Victim is logged into bank.com; browser holds the session cookie.
  • 2 · Victim wanders onto evil.com.
  • 3 · evil.com silently auto-submits a hidden form to bank.com: "transfer money".
  • 4 · Browser attaches the bank cookie → bank sees a valid request → money gone.
  • SameSite=Lax — cookie is not sent on cross-site requests → CSRF neutralized.
  • HttpOnly — JavaScript (XSS) can't read it via document.cookie.
  • Secure — cookie only travels over HTTPS → no plaintext leak on :80.
force the flags if the app doesn't set them
<IfModule mod_headers.c>
  Header edit Set-Cookie ^(.*)$ \
    "$1; SameSite=Lax; Secure; HttpOnly"
</IfModule>
▶ DEMOCheck in F12 → Application → Cookies: the HttpOnly, Secure and SameSite columns are all set.
34Security

firewalld & SELinux — the CentOS gatekeepers

the two things beginners forget
# 1) firewalld — open the ports
# firewall-cmd --permanent --add-service={http,https}
# firewall-cmd --reload

# 2) SELinux — enforcing by default on CentOS
# setsebool -P httpd_can_network_connect 1   # allow proxy
# semanage fcontext -a -t httpd_sys_content_t \
     "/srv/web(/.*)?"
# restorecon -Rv /srv/web                     # apply context
# semanage port -a -t http_port_t -p tcp 8080  # serve on :8080

Don't disable SELinux to "fix" a problem. Learn ausearch / audit2why — the denial log tells you exactly which boolean or context to set.

Same roles, different names:

Ubuntu: install → configure → TLS → test
# 1  INSTALL
$ sudo apt update && sudo apt install apache2 -y
$ sudo systemctl enable --now apache2
$ sudo ufw allow 'Apache Full'          # open 80 + 443

# 2  CONFIGURE the site
$ sudo mkdir -p /var/www/demo
$ echo "Hello HCMUS" | sudo tee /var/www/demo/index.html
$ sudo vi /etc/apache2/sites-available/demo.conf
$ sudo a2ensite demo                     # enable the site
$ sudo a2enmod ssl proxy proxy_http headers
$ sudo apache2ctl configtest && sudo systemctl reload apache2

# 3  HTTPS
$ sudo apt install certbot python3-certbot-apache -y
$ sudo certbot --apache -d demo.hcmus.edu.vn

# 4  TEST
$ systemctl is-active apache2
$ ss -tlnp | grep ':80\|:443'
$ curl -I http://localhost/

Ubuntu has no SELinux — just make sure files are readable by www-data (never chmod 777). Enable sites/modules with a2ensite / a2enmod instead of editing include files by hand.

A tiny Node backend for /api

1 · the Node backend
# install Node from CentOS AppStream
[root@centos ~]# dnf install nodejs -y

# /opt/api/api.js  — bind to localhost ONLY
const http = require('http');
http.createServer((req, res) => {
  res.setHeader('Content-Type','application/json');
  res.end(JSON.stringify({ ok:true, path:req.url }));
}).listen(3000, '127.0.0.1');

[root@centos ~]# node /opt/api/api.js &   # run
2 · /etc/httpd/conf.d/demo.conf (inside vhost)
# in the demo vhost (mod_proxy loaded by default)
ProxyPreserveHost On
ProxyPass        /api  http://127.0.0.1:3000/
ProxyPassReverse /api  http://127.0.0.1:3000/

# SELinux: let httpd open a network socket
# setsebool -P httpd_can_network_connect 1

# curl localhost/api/hello
{"ok":true,"path":"/hello"}

Bẫy #1 trên CentOS: quên httpd_can_network_connect → Apache bị SELinux chặn, /api trả 503 dù Node đang chạy. Backend chỉ nghe 127.0.0.1 nên không ai chạm thẳng vào :3000 — mọi request phải đi qua Apache.
