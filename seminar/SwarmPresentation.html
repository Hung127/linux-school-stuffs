Nhập môn: Container và Docker là gì?

Container

Một "gói" chạy được của ứng dụng: code + thư viện + cấu hình, tách biệt với phần còn lại của máy.

Giống thùng container trên tàu biển: hàng bên trong khác nhau, nhưng thùng chuẩn nên cảng nào cũng bốc được.

Image

Bản mẫu chỉ-đọc dùng để tạo container, ví dụ nginx:alpine.

Giống công thức nấu ăn hay khuôn bánh: một khuôn làm ra nhiều chiếc bánh giống hệt nhau.

Docker Engine

Phần mềm tạo, chạy và dừng container trên một máy.

Giống cần cẩu ở cảng: xếp và dỡ từng thùng, nhưng chỉ ở một bến.

Vấn đề: Docker Engine chỉ lo một máy. Khi cần chạy hàng chục container trên nhiều máy, ta cần thêm một "người điều phối" — đó là Docker Swarm.

Mục tiêu slide: ai chưa từng dùng Docker vẫn theo kịp phần sau. Ba từ cần nhớ: Container (thùng hàng), Image (khuôn mẫu), Docker Engine (cần cẩu một bến). Câu chốt: Engine chỉ lo một máy, cần thêm lớp điều phối cho nhiều máy.

Docker Swarm là gì? Hãy nghĩ tới một nhà hàng

Docker Swarm là chế độ cụm có sẵn trong Docker Engine: gom nhiều máy thành một nhóm. Bạn chỉ nói "cần 3 bản sao của app" — Swarm tự chia việc cho các máy và luôn giữ đủ 3 bản, như bếp trưởng lo đủ 3 đĩa cho khách.

Dùng hình nhà hàng xuyên suốt buổi: khách chỉ gọi món (khai báo kết quả), bếp trưởng (Manager) quyết định ai nấu, đầu bếp (Worker) nấu. Một đĩa = một Task. Hỏi lớp: nếu đầu bếp A nghỉ đột xuất thì sao? → bếp trưởng giao các đĩa cho người còn lại — đó chính là demo 4.

Đây là bảng tra cứu để cả lớp cùng ngôn ngữ trước khi vào lý thuyết. Chỉ vào hình: một Service, ba Task, rải trên hai Node. Từ đây trở đi mỗi khi nói "Task" là nói "một đĩa cụ thể", "Service" là "món trong thực đơn".

Vì sao docker run một máy không đủ cho đợt sale?

docker run — một máy

  • Chỉ một host, một container cho mỗi service
  • Muốn thêm bản sao thì tự gõ lệnh docker run
  • Container chết thì phải tự đứng dậy thay
  • IP container đổi mỗi lần restart
  • Mật khẩu nằm trong biến môi trường, lộ khi inspect

Production — cần có

  • Nhiều host, workload trải đều nhiều máy
  • Khai báo "3 replicas", hệ thống tự đạt tới
  • Tự phát hiện sự cố và tạo lại Task
  • Một địa chỉ IP ổn định cho cả service
  • Secret được mount vào container, không nằm trong lệnh

Container Orchestration = lớp điều phối giữa "lệnh bạn gõ" và "trạng thái hệ thống thực sự". Docker Swarm là lớp đó, dùng chính Docker Engine, không cài thêm gì.

Điểm mấu chốt: người dùng khai báo KẾT QUẢ (3 replicas), không khai báo CÁCH LÀM. Swarm lo phần "cách làm". Đó là toàn bộ khác biệt giữa `docker run` và orchestration. Hỏi lớp: "Nếu app của các bạn chạy 3 bản sao, ai sẽ chạy lệnh khi 1 container chết?" — câu trả lời "phải có người can thiệp" chính là lập luận cần orchestration. Lưu ý: Swarm là built-in của Docker Engine, cùng một `dockerd`, không phải Kubernetes. Nói rõ để lớp không nghĩ phải cài thêm gì.

Manager & Worker: Desired State được hiệu chỉnh liên tục

Manager Node

Orchestrator · Scheduler · Dispatcher

Lưu Desired State trong Raft store, lập lịch Task, cấp lệnh xuống Worker. Mặc định cũng chạy Task được như một Worker.

Worker Node

Agent · Docker Engine

Chạy Task được giao, gửi Heartbeat kèm trạng thái mỗi ~5 giây. Không tự quyết định — chờ Manager lệnh.

Desired State 3 replicas · nginx:alpine
→
Actual State 2 replicas — 1 Task vừa chết
→
Orchestrator + Scheduler Tạo Task mới → đặt lên Node còn sống → Actual trở lại = Desired

Reconciliation = vòng lặp so sánh Actual với Desired, lặp lại liên tục. Khi sự cố xảy ra, Desired State không hề thay đổi — chỉ Actual State bị suy giảm.

Hai vế của bài học: 1) Phân vai: Manager = bộ não (không chạy app là mục đích, nhưng mặc định vẫn chạy được), Worker = cơ tay (chạy Task, báo cáo trạng thái). 2) Reconciliation: Desired State là cái bạn khai, Actual State là cái đang chạy. Swarm liên tục ép Actual về Desired. Khi có sự cố, Desired không đổi — đó là lý do hệ thống tự phục hồi được mà không cần ai can thiệp. Câu hỏi hay cho lớp: "Nếu Manager chết thì sao?" → Trả lời: một Manager là điểm lỗi đơn của control plane; cần 3 Manager (quorum) cho production. Nói thêm một câu, đừng đi sâu — phần HA thuộc module khác. Demo 4 sẽ chứng minh đúng cái vòng lặp này bằng hành vi quan sát được.

Demo 1a — Khởi tạo cụm và deploy service 3 replicas

VM1 · Managerbước 1–2
$ docker swarm init --advertise-addr MANAGER_IP
$ docker swarm join-token worker
→ in ra lệnh join dành cho Worker
VM2 · Workerbước 3
$ docker swarm join \
    --token WORKER_TOKEN MANAGER_IP:2377
→ This node joined a swarm as a worker.
VM1 · Managerbước 4
$ docker service create \
    --name web --replicas 3 \
    --publish published=8080,target=80 \
    --update-parallelism 1 --update-delay 5s \
    --update-order start-first \
    nginx:1.26-alpine
VM1 · Managerbước 5
$ docker node ls
$ docker service ls
→ 2 node Ready · web 3/3
Thao tác tay, dừng sau mỗi lệnh để lớp đọc output. Sau `swarm init`: output có "This node is a manager" và cảnh báo "Only advertise address is set" — bảo các bạn bỏ qua, chỉ cảnh báo. Sau `join`: Worker in ra "This node joined a swarm as a worker." Nếu treo → kiểm tra port 2377. Sau `service create`: đợi vài giây rồi `docker service ls` phải ra `3/3`. Nếu là `0/3` hoặc `3/3` nhưng Pending → xem `docker service ps web`. `docker node ls` phải có 2 dòng, cả hai Ready, dòng đầu có dấu `*` là Leader. Giải thích nhanh tham số publish: published=8080 (port trên host), target=80 (port trong container nginx).

Routing Mesh: truy cập Service từ IP của bất kỳ Node nào

Client curl http://MANAGER_IP:8080 curl http://WORKER_IP:8080
→
Node manager ingress :8080
Node worker ingress :8080
→
Overlay network VXLAN · 4789/udpmạng ảnh trên nhiều host
web.1 web.2 web.3

Mỗi Node có một ingress lắng nghe port đã publish. Request đến IP của node nào cũng được — Routing Mesh chuyển tiếp qua overlay tới một Task đang chạy, kể cả node đó không có replica nào.

Overlay network là mạng ảnh lớp 2 chạy trên các container của nhiều host khác nhau, đóng gói bằng VXLAN trên UDP 4789. Container ở VM1 "thấy" container ở VM2 như thể cùng một switch. Routing Mesh là lớp định tuyến trên đó: port publish không gắn vào container cụ thể mà gắn vào ingress của mọi node trong cụm. Hệ quả quan trọng: client không cần biết Task nào đang chạy, và ta có thể publish một service trên nhiều node. Đây cũng là lý do demo 1 curl được cả hai IP. Nói thêm một câu về đánh đổi: routing qua ingress có chi phí, với hệ thống cực lớn thì người ta hay dùng overlay + service DNS thay vì publish port. Nhưng ở mức seminar này thì publish port là cách trực quan nhất.

Rolling Update: cập nhật dần, không dừng cả service

Tham sốÝ nghĩaẢnh hưởng
--update-parallelism N Số Task được thay thế đồng thời 1 = cập nhật tuần tự, an toàn nhất
--update-delay 5s Thời gian chờ giữa hai lượt cập nhật Để Task mới ổn định trước khi dừng Task cũ
--update-order start-first Khởi động Task mới trước, dừng Task cũ sau Luôn có Task sẵn sàng phục vụ trong lúc rollout
--update-failure-action pause Dừng rollout khi Task mới lỗi Không lan tay sai một bản release hỏng

Zero-downtime là kết quả quan sát được, không phải cam kết của cấu hình. Nó còn phụ thuộc ứng dụng (session, kết nối DB), health check, tài nguyên. Vì vậy demo 2 đo bằng log thật chứ không nói suông.

Giải thích trực giác của start-first: với stop-first, giữa lúc Task cũ dừng và Task mới lên, service có thể không còn Task nào → request rơi. Với start-first, Task mới đã chạy và sẵn sàng thì Task cũ mới bị dừng. update-parallelism = 1 nghĩa là tuần tự hoàn toàn: mất nhiều thời gian hơn (3 task × 5s delay) nhưng không bao giờ giảm số Task đang phục vụ. update-delay là khoảng nghỉ giữa các lượt, không phải timeout của Task. Nói rõ để lớp không nhầm. Câu hỏi: "Tăng parallelism lên 3 thì được không?" → Được, nhanh hơn, nhưng giảm độ an toàn và tăng rủi ro lỗi tài nguyên. Tùy hệ thống.

Demo 2 — Rolling Update v1 → v2, đo gián đoạn bằng log thật

Terminal 2 · Clientchạy song song
$ while true; do
  printf '%s ' "$(date '+%H:%M:%S')"
  curl --max-time 2 -s -o /dev/null \
    -w '%{http_code}\n' http://MANAGER_IP:8080 \
    || echo "CURL_FAILED"
  sleep 0.2
done | tee rolling-update.log
VM1 · Managercập nhật
$ docker service update \
    --image nginx:1.28-alpine \
    --update-parallelism 1 \
    --update-delay 5s \
    --update-order start-first \
    --update-failure-action pause \
    web
VM1 · Managertheo dõi
$ docker service ps web
web.1  1.26  Shutdown
web.1  1.28  Running  ← task mới
Thứ tự: mở terminal thứ hai, chạy vòng lặp curl TRƯỚC, rồi mới update. Nếu update trước thì log sẽ không bắt được giai đoạn chuyển tiếp. Vòng lặp ghi ra: timestamp + mã HTTP, hoặc CURL_FAILED nếu request lỗi. `tee` vừa in ra màn hình vừa lưu file — lớp thấy log chạy ngay và sau đó mình phân tích file. Sau khi update xong, `docker service ps web` sẽ có cả Task cũ (Shutdown) và Task mới (Running) cho cùng một slot. Chỉ vào cặp Task đó: cùng tên slot web.1, nhưng Task ID khác nhau. Giải thích: Task trong Swarm là bất biến (immutable). Swarm không khởi động lại Task cũ, mà tạo Task mới cho cùng một slot. Dừng vòng lặp curl bằng Ctrl+C sau khi update xong, rồi sang slide kế tiếp để phân tích log.

498/498 request thành công, 0 lỗi trong suốt quá trình rollout. Đây là bằng chứng đo được, không phải lời hứa của cấu hình.

Đây là slide "chứng minh". Số liệu 498/0 là ví dụ minh hoạ — trên lớp thật sẽ là con số khác, nhưng tỉ lệ 100% là điều cần đạt. Nếu lớp thấy có CURL_FAILED: đừng giấu, phân tích. Thường do Task chưa sẵn sàng nhận traffic (thiếu health check), ứng dụng cần thời gian khởi động, hoặc tài nguyên 1 GB bị tranh chấp lúc cả 4 Task cùng chạy. Đây là điểm dạy: "zero-downtime" phụ thuộc cả cấu hình lẫn ứng dụng và tài nguyên. Nếu thêm `--health-cmd` thì Swarm còn chỉ đưa traffic vào Task đã khoẻ. Liên hệ về đổi image: nếu image tag không đổi (ví dụ vẫn là :latest) thì Swarm sẽ không rollout lại, vì nó so sánh theo digest. Dùng tag có version khác như ở đây.
Chương 3 · Docker Secret

Mật khẩu database không nên nằm trong lệnh

Tình huống

Bạn thực tập gõ docker run -e DB_PASSWORD=... rồi chụp màn hình gửi nhóm Zalo cho tiện. Từ lúc đó, ai trong nhóm hay ai chạy docker inspect đều thấy mật khẩu.

Giống dán mật khẩu wifi lên cửa kính quán: tiện, nhưng ai đi ngang cũng thấy.

Câu hỏi cho lớp

Mật khẩu nên nằm ở đâu để Service dùng được mà không ai vô tình nhìn thấy?

Ta sẽ học rồi làm ngay

Docker Secret: vòng đời từ lệnh tạo đến file trong container. Rồi demo tạo secret và đọc tại /run/secrets.

Hỏi lớp: bạn nào từng lỡ push file .env hoặc gửi mật khẩu qua chat? Dẫn vào lý thuyết Secret rồi demo 3.

Secret: giữ mật khẩu ngoài lệnh và ngoài image

Secret là gì?

Dữ liệu nhạy cảm (mật khẩu DB, API key, chứng chỉ) do Swarm giữ và chỉ giao cho Task được cấp quyền.

Như két sắt có phát chìa: ai được cấp mới mở được, không dán mật khẩu lên màn hình.

Biến môi trường (-e)
  • Lộ khi chạy docker inspect
  • Nằm trong shell history và log
  • Có thể bị đóng vào image
Docker Secret
  • Giá trị không nằm trong lệnh hay image
  • Chỉ ở RAM của Task được cấp
  • Xoá sạch khi Task dừng

Secret bất biến: muốn đổi mật khẩu phải tạo secret mới rồi --secret-rm / --secret-add. Ai vào được container vẫn đọc được file, nên secret tốt hơn env var chứ chưa phải hoàn hảo.

Lý thuyết cho demo 3. Ba ý: (1) secret được tạo ở Manager, lưu trong Raft store đã mã hoá; (2) Swarm chỉ gửi secret tới Node đang chạy Task cần nó; (3) trong container, secret là file nằm trên tmpfs (RAM) ở /run/secrets/<tên>, mất khi Task dừng. So sánh với biến môi trường: env var hiện trong docker inspect. Nói thật giới hạn: secret không sửa tại chỗ, và ai đọc được trong container thì đọc được file.

Lưu ý giới hạn (như cũ): secret được mã hoá trong Raft store của Manager, nhưng bất kỳ ai vào được container cũng đọc được file; secret không sửa tại chỗ — phải tạo secret mới rồi --secret-rm / --secret-add. Chương 4 · Tự phục hồi

20h tối, máy chủ mất điện

Tình huống

Đúng giờ cao điểm, một máy chủ tắt đột ngột. Nhân viên đã nghỉ, không ai trực để gõ lệnh dựng lại. Khách vẫn đang đặt trà sữa.

Giống một ca trực nghỉ đột xuất: trưởng ca lập tức điều người ca khác sang, khách không phải chờ.

Câu hỏi cho lớp

Hệ thống phát hiện sự cố bằng cách nào, và mất bao lâu để đủ số bản sao trở lại?

Ta sẽ học rồi làm ngay

Container Failure khác Node Failure ra sao, Heartbeat và Reconciliation. Rồi demo tắt hẳn VM Worker.

Chương cuối, gom lại ý Desired State đã học ở chương 1. Dẫn vào lý thuyết rồi demo 4: tắt cứng VM, không dùng docker stop.

Tự phục hồi: khi container hoặc cả Node gặp sự cố

Container Failure

Tiến trình trong container thoát hoặc health check lỗi, nhưng Node vẫn sống. Swarm tạo Task mới thay thế, thường chỉ vài giây.

Như một cầu thủ bị thẻ đỏ: sân vẫn nguyên, chỉ cần người khác vào.

Node Failure

Cả máy mất điện hoặc mất mạng, mọi Task trên máy biến mất cùng lúc. Manager phát hiện qua Heartbeat rồi dồn Task sang Node còn sống.

Như cả một ca trực nghỉ ốm: cần người ca khác sang gánh.

Desired State vẫn là 3. Swarm chỉ phục hồi được khi còn đủ tài nguyên (1 GB RAM!) và còn Manager. Nó cũng không tự dời Task về Worker khi Worker sống lại.

Lý thuyết cho demo 4. Phân biệt hai loại sự cố: Container Failure (Node vẫn heartbeat bình thường) và Node Failure (mất heartbeat, Node = Down). Demo 4 là Node Failure. Bốn bước ở hình: Heartbeat ~5 giây, mất liên lạc quá hạn thì Down, Orchestrator tạo Task mới (Task cũ chuyển Shutdown, không restart lại), Scheduler đặt lên Node còn sống. Nhấn mạnh: Desired State không đổi, chỉ Actual State giảm. Nhắc giới hạn: thiếu RAM thì Task mới kẹt Pending; một Manager là điểm lỗi đơn.

Manager phát hiện bằng Heartbeat timeout: Worker gửi nhịp tim mỗi ~5 giây; mất liên lạc quá hạn thì node chuyển sang STATUS = Down. Không phải phát hiện tức thì — có độ trễ.

Bước này cần cẩn thận: tắt đột ngột VM, không phải `docker stop`. Nếu chỉ dừng container thì đó là Container Failure (demo khác), không phải Node Failure — Worker vẫn heartbeat bình thường và Manager không đánh dấu Down. Cách tắt tốt nhất trong phòng máy: dùng lệnh shutdown của hypervisor, hoặc `sudo poweroff`. Nếu dùng `sudo shutdown -h now` mà VM đã tắt sạch thì Manager phải chờ heartbeat timeout. Giải thích cơ chế: Worker Agent gửi heartbeat mỗi ~5 giây kèm trạng thái các Task. Manager hết hạn → đánh dấu Down. Khoảng 15–20 giây là con số quan sát được trong thực tế, có thể lâu hơn tuỳ mạng. Chạy `watch -n 2` để lớp thấy node đổi trạng thái ngay trên màn hình. Đợi đến khi thấy Down rồi mới sang slide kế tiếp.

Demo 4b — Swarm tự tạo Task thay thế trên Node còn sống

VM1 · Managersau khi Worker chết
$ docker service ps web
web.1  Shutdown  worker
web.2  Shutdown  worker
web.1  Running   manager  ← mới
web.2  Running   manager  ← mới
web.3  Running   manager

$ docker service ls
web  replicated  3/3

Desired State = 3 không đổi. Actual State tụt xuống khi Worker chết; Orchestrator tạo Task mới (Task ID mới, cùng tên slot) và Scheduler đặt lên Node còn sống.

Hai điều cần biết: Manager mặc định cũng chạy Task được (availability Active). Và Swarm không tự dời Task về lại Worker khi Worker sống lại — muốn cân bằng thì docker service update --force web.

Kết quả cần chỉ ra: Task cũ trên Worker ở trạng thái Shutdown, Task mới có Task ID khác nhưng cùng tên slot (web.1, web.2), và toàn bộ dồn về Manager. Nói rõ: Task là bất biến. Swarm không restart Task cũ mà tạo Task mới — vì Task cũ giữ lại lịch sử để điều tra. Nói rõ về giới hạn: nếu Manager không đủ tài nguyên cho 3 Task (chỉ 1 GB RAM!), Task mới sẽ kẹt ở trạng thái Pending và service sẽ là 2/3. Đó là giới hạn hạ tầng, không phải lỗi Swarm. Nếu bị vậy, nói thẳng với lớp: "đây là lý do yêu cầu hạ tầng của đề bài là 2 VM × 1 GB". Hiện tượng non-rebalancing: Worker sống lại thì Task vẫn nằm ở Manager, vì dời lại sẽ gây gián đoạn không cần thiết. Dùng --force nếu muốn cân bằng lại. Câu hỏi kết: "Nếu cả Manager lại chết thì sao?" → Không còn Manager thì không ai điều phối được; đó là lý do production cần 3 Manager (quorum Raft). Nối lại phần HA ở module 6.

Swarm hay Kubernetes? Hai mức độ của cùng một bài toán

Docker Swarm

  • Cài đặt: có sẵn trong Docker Engine — docker swarm init là xong
  • Vận hành: ít thành phần, học nhanh, ít thao tác
  • Quy mô: cụm nhỏ – vừa, vài chục node
  • Chọn khi: học orchestration, hệ thống nhỏ, team đã dùng Docker

Kubernetes (K8s)

  • Cài đặt: nhiều thành phần — kubelet, etcd, API server
  • Vận hành: phức tạp, cả hệ sinh thái YAML
  • Quy mô: hàng nghìn node, chuẩn ngành production
  • Chọn khi: hệ thống lớn, cần ecosystem (Helm, auto-scaling)

Chọn theo bài toán, không theo trend: Swarm như quán trà sữa 2 quầy tự điều phối — đủ cho nhu cầu hiện tại; Kubernetes như chuỗi hàng trăm quán có bộ máy quản lý riêng. Quan trọng hơn: bốn khái niệm đã học chuyển thẳng sang K8s, chỉ đổi tên gọi — service → Deployment, secret → Secret, rolling update là mặc định, self-heal tự có.

Slide mở rộng, trả lời câu hỏi hay gặp: "Vì sao seminar chọn Swarm mà không phải Kubernetes?" Hai công cụ giải cùng một bài toán — điều phối container — ở hai quy mô khác nhau. Swarm: có sẵn trong Docker Engine, một lệnh swarm init là có cụm. Đủ để chứng minh cả bốn khái niệm của buổi học. Kubernetes: chuẩn ngành, hệ sinh thái lớn nhất (Helm, auto-scaling, operator), nhưng để chạy cần cả bộ: kubelet, etcd, API server. Nhấn mạnh: chọn Swarm không phải vì K8s kém, mà vì bài toán 2 VM × 1 GB không cần K8s. Chọn công cụ theo bài toán, không theo trend. Chốt quan trọng nhất: hôm nay học khái niệm, không học riêng một công cụ. Sang K8s: service của Swarm ~ Deployment của K8s; secret vẫn là Secret; rolling update là mặc định của Deployment; self-heal là ReplicaSet tự tạo pod mới. Ai theo kịp bốn chương hôm nay sẽ đọc được manifest Kubernetes mà không bối rối.
